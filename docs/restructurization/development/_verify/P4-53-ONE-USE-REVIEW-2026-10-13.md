# P4-53 One-Use Retry Unit Review

Status: source review complete; no source edits, tests, builds, or runtime operations performed. This report does not close tasks or gates.

Scope: `arcana-core/src/agent/recovery_snapshot.rs`, `db/runs.rs`, `db/tasks.rs`, `agent/tool_executor.rs`, and `agent/builtin_tools/{claim_task_tool,reconcile_worker_operation,list_worker_health,write_file}.rs`, against ADR-0380/0382 and the assigned safety contract.

## Review result

No confirmed provider-reachable authorization bypass, grant double-consumption path, lock inversion, argument mismatch, or completion-guard bypass was found in the reviewed retry flow.

The focused follow-up resolves the previously reported run-binding gap at the admission and consume boundaries. `RETRY_ADMISSION_GRANT_SQL` now requires a `fleet-tick` run whose persisted host/PID match the current process, plus a joined `worker_run_state` for the grant worker in an active phase and task attribution that is absent or matches the original task. The SQLite consume trigger repeats the worker kind/state/phase/worker/task checks and calls an authorization UDF that verifies the stored PID/host against the current process. Grant creation also rejects non-worker origin runs and snapshots without an explicit owner. I found no concrete regression in these predicates: they retain the normal active phases (`starting`, `retrying`, `running`) and permit task attribution to remain null before it is recorded, while still rejecting attribution to a different task. This resolves the reported gap by source inspection; the final focused build/tests remain root-owned and were not run or independently verified here.

## Source evidence

- `recovery_snapshot.rs`: `verify_retry_admission` rejects non-v2 originals and requires the new write's relative path, content digest, and overwrite flag to match the sealed expectation. `verify_state` compares task identity, assigned worker, dependencies, workspace/root identity, Git state and checkpoint continuity. For retry, it requires the task to be `in_progress`, assigned to that worker, claimed by the current process PID and current hostname, the original workspace fingerprint to match, and the target's current `FileState` to equal the sealed prestate. The operation must be exactly `write_file` and enabled hooks must be absent. Legacy v1 snapshots cannot authorize retry.
- `tool_executor.rs`: retry cursors are accepted only for `write_file`; they must be positive, have a run ID, and the run actor must equal the executor role. The executor acquires the workspace write lease before journaling, retains it through the handler/outcome path, and derives a single jailed relative target plus the actual path/content/overwrite values. Other tools reject the cursor.
- `runs.rs`: retry admission holds an immediate Tasks transaction before an immediate Runs transaction, verifies the original snapshot while the task lock and workspace lease are held, then inserts the replacement intent with the grant FK in the same Runs transaction. The unique partial index prevents reusing one grant. The consume trigger also matches task, operation, effect, and target paths; RAII clears the connection-local authorization bit on success or error. The unresolved-operation queries suppress the original only after a grant is consumed, so an unused grant remains held and a new unknown replacement intent blocks further claims and completion.
- `reconcile_worker_operation.rs` and `runs.rs`: only the Supervisor path can append a reconciliation; positive decisions require the original run closed, a matching original intent/snapshot/task owner, selected workspace lease, immediate task lock, and snapshot verification. Reconciliation insertion only accepts an unknown intent with no prior reconciliation. Legacy/absent snapshots cannot grant retry; `do_not_retry` appends a hold decision without authorizing replay.
- `claim_task_tool.rs`: identity is checked against the assigned worker before consulting RunsDb. The retry grant permits that owner past only the specific original blocker; any other unresolved side effect still refuses the claim. Atomic task claim then records process PID/host, which admission rechecks.
- `write_file.rs`: the handler uses the same path/content/overwrite arguments represented in the retry snapshot and still requires the current task claim before checkpoint/write. It keeps the path lock and path jail.
- `tasks.rs` and `runs.rs`: the task status trigger blocks transitions into `qc_review`/`done` while any non-Board effect is unknown and unreconciled, except an original whose grant has been consumed. The replacement intent remains independently visible to the same query. The UDF reads the colocated RunsDb read-only; unreadable/incompatible state fails closed, and missing RunsDb is treated as no recorded journal.
- `list_worker_health.rs`: journal entries expose retry grant/consuming cursors and mark an unknown original as no longer recovery-required only after consumption. The replacement run's own unknown intent remains recovery-required. Pages are run-scoped, so callers must continue paging the latest worker run to see its retry entry.

## Focused follow-up: persisted replacement-run binding

Reviewed the exact changed admission predicate in RETRY_ADMISSION_GRANT_SQL, migration 10 consume trigger, process-identity UDF, and retry-grant creation checks. The checks now bind the new intent to the live same-worker fleet run, matching active worker state, current host/PID, and compatible task attribution. The consume trigger independently rejects inserts without those persisted conditions and the current-process authorization callback. No concrete source regression found. ADR-0383 records this bounded fix. This is source review only; no test/build evidence is added by this follow-up.
