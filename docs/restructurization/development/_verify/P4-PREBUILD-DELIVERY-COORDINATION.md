- **P4-12 — CONFIRMED.** The current build-evidence store is still process-memory-only: `build_evidence.rs:88-90` defines a `OnceLock<Mutex<HashMap<...>>>`; `record` inserts only into that map (`:241-256`) and readers retrieve only from it (`:262-274`). A process restart loses the evidence. TG4-07's restart-survival requirement remains unimplemented; preserve this task.
- **P4-13 — PARTIALLY CONFIRMED; wording stale.** The named `str::contains` false-positive classifier was replaced by segment/token-prefix matching (`build_evidence.rs:102-115, 146-163`), so the example `git commit -m "cargo build fixes"` no longer describes the present classifier. The command result exit code is stored (`:241-251`). Reframe the task around proving that evidence is attached to the actual spawned build invocation and its exit status; do not retain the obsolete exact defect claim.
- **P4-14 — PARTIALLY CONFIRMED.** There is a real production reader: `update_task_status_tool.rs:149-168, 183-219` calls `most_recent_build` before `qc_review`. But it reads the transient process-memory ring, not a persisted table (`build_evidence.rs:262-274`). P4-14 should depend on P4-12's durable store and require the guard to read that persisted record.
- **P4-22 — REFUTED as a current defect claim.** `ToolContext.agent_role` is now a required `String`, with a comment explicitly saying every agent has an identity (`arcana-core/src/agent/tool_trait.rs:70-75`); the repository has two production `ToolContext` construction sites in `tool_executor.rs:415,557`. The task's assertion that identity is set only by the deleted MCP adapter is stale. Keep only any still-needed ACP behavior proof, and distinguish that from identity plumbing.
- **P4-30 — CONFIRMED.** `defaults.rs:43-45` explicitly documents that defaults always overwrite, and `:48-62` calls `save_recipe` unconditionally for each built-in recipe. User-edited recipes are still overwritten at initialization. This is a concrete live behavior, not just stale commentary.
- **P4-32 — CONFIRMED in its central claim.** The Supervisor's live recipe uses a static Routing Matrix, calls `suggest_worker` only for “ambiguous” tasks, and explicitly says not to call it for tasks the matrix disambiguates (`defaults.rs:332-345`). The assignment tool requires a `worker_slug` (`assign_task.rs:41-55, 58-65`). Thus the deterministic scorer is not authoritative for ordinary dispatch; task remains relevant. Current exact prompt wording may have changed from the plan's “skip scorer” paraphrase, so quote the current source when updating it.
- **P4-33 — CONFIRMED.** `select_worker` accepts a static match only when `static_conf > 0.85` (`routing/scorer.rs:134-149`), while shipped pattern confidences top out at exactly `0.85` (`routing/patterns.rs:10-47`; remaining entries are lower, `:48-97`). Therefore no current pattern can yield `method: "static"` through this branch.
- **P4-41 — CONFIRMED for Supervisor reachability; one subclaim not fully checked.** The Supervisor recipe's request handler decomposes with flat `create_task` (`defaults.rs:315-318`), and its listed tools omit `create_epic` / `create_phased_task` (`:431-445`), while those tools are globally registered (`builtin_tools/mod.rs:166-167`). Registration alone does not make them reachable through the Supervisor prompt. I did not inspect all frontend action paths, so the “no frontend caller” clause remains unverified.
- **P4-44 — CONFIRMED as unwired.** `ToolExecutor` defaults `procedural_recall` to false and documents P4-44 as the enabling caller (`tool_executor.rs:104-115`); retrieval exits immediately when false (`:137-149`). Repository search found no production `.with_procedural_recall(true)` call. The field/seam exists, but the claimed worker benefit is not active.

## Resumed source audit — delivery and coordination claims

- **P4-11 — PARTIALLY CONFIRMED.** `platform/command.rs:25-31,108-153` has intent-to-argv mappings and `:163-175` resolves npm-family Windows shims; its tests are in the same module (`:228-298,365+`). But the only repository references found for `CommandIntent`/`platform::command` are the definitions/tests and the CI gate's source scan (`rg -n 'CommandIntent|platform::command|platform::resolve' arcana-core/src src-tauri/src`); production Bash still executes model-authored shell via `cmd /C` on Windows or `sh -c` elsewhere (`agent/builtin_tools/bash.rs:124-145`). `runner.rs:537-545` tells recipes to issue shell validation commands. So the platform mapper exists and is unit-tested, but ecosystem detection + Rust-owned argv are not wired into production command execution. P4-11 remains, though “ecosystem detection” must be implemented/verified separately from the current mapper.
- **P4-15 — CONFIRMED as missing behavior.** The live Supervisor retry policy requeues build failures while `retry_count < 3`, then leaves the task `build_failed` for manual review (`recipes/defaults.rs:393-398`). The worker recipe directs the worker to stop and let the retry policy re-dispatch (`:583-591`); no inspected path invokes a diagnostic step after three consecutive failures. The existing prose “Exhausted 3 attempts → failed” (`:598-602`) does not prove a bounded diagnostic loop. TG4-08 should prove the real third-failure branch and that Rust remains the invocation/verdict owner.
- **P4-16 — CONFIRMED.** Active worker instructions still contain platform-sensitive shell forms: `defaults.rs:543` uses `&&`; `:552-553` names POSIX `source` and shell forms; `:578` contains `timeout`, redirection, `grep`, `||`; and the broader prompt includes POSIX `tee` forms (`:567-570`). `bash.rs:138-145` dispatches Windows commands to `cmd /C`, so the compatibility risk in P4-16/TG4-17 is still real. Scope the gate to active recipes/skills/tool prompts after excluding the historical design archive.
- **P4-17 — CONFIRMED.** The shared setting reader still deliberately collapses unset and database error to an empty string (`db/app_settings.rs:69-75`). The recipe runner then falls back to `~/.arcana/agents/<slug>` (`recipes/runner.rs:187-210`), while its own comment admits workers and the PA share the configured root (`:189-195`). This does not meet “one resolver that fails loudly”; path/error behavior needs a production-level contract.
- **P4-18 — PARTIALLY CONFIRMED.** Built-in file tools such as `append_file` resolve relative to `ctx.working_dir` and call the path validator (`append_file.rs:71-87`); `bash.rs` instead runs arbitrary shell in that working directory (`:105-120,138-168`) and the source explicitly says the alleged cwd jail compares the directory to itself (`:90-119`). The task's broad “every agent write/no CWD-relative writes” claim remains plausible, but the complete set of mutation channels and acceptable absolute paths needs an exhaustive inventory before narrowing it.
- **P4-19 — CONFIRMED.** `auto_checkpoint_before_write` is called immediately before writes without checking a `Result` (`write_file.rs:131-137`; the helper signature returns `()` at `git/checkpoint.rs:246`). Thus checkpoint failure cannot veto this write path. Verify the same invariant across `edit_file` and `append_file` when implementing.
- **P4-20 — OVERSTATED / unresolved architecture decision.** P4-20 mandates a separate branch per task, but active recipe source says all workers receive the same checkout and explicitly rejects task worktrees/locks as conflicting with that model (`recipes/defaults.rs:81-91`); P8's commit protocol recorded “one branch for the whole fleet, not one per task” and named ADR-0040 (`MDP §P8-38 closeout`, current paragraph near P4 section's downstream notes). A shared checkout cannot safely switch branches concurrently. The plan needs an owner ruling on per-task isolation versus shared-branch policy before this can be scheduled; I do not choose between them.
- **P4-21 — PARTIALLY CONFIRMED.** The only literal `ide:navigate` source hit is an emitter in `src-tauri/src/commands/graph_commands.rs:1108` (full source-tree exact-string search found no frontend listener). The end-to-end handoff is therefore unproven. Search cannot exclude a dynamically named listener, so confirm by tracing all event subscriptions and the IDE/open-and-run consumer. Preserve the run-from-IDE smoke, which is stronger than an event-name test.
- **P4-23 — CONFIRMED.** `list_worker_messages_for` returns pending rows after transitioning them to `read` (`db/tasks.rs:954-1008`), and acknowledgement is a separate operation (`:1011-1025`). If the consumer stops between read and acknowledgement, the default inbox call filters to pending only (`list_worker_messages.rs:41-49,65-83`). A stale-reader helper exists (`db/tasks.rs:1028-1047`) but exhaustive reference search found only its definition, no production caller. Therefore “once-and-only-once” and “wire the stale-message reader” are still real behaviors to settle; prove recovery through the worker recipe consumer, not just the DB method.
- **P4-24 — UNRESOLVED, requires a liveness proof.** The Supervisor tells itself to stop after handling any request (`recipes/defaults.rs:311-321`), and its stop condition requires no pending requests (`:413-421`). That bounds each tick's work but does not alone prove dispatch progresses if request resolution fails or if the queue is continuously replenished. Keep TG4-12's adversarial “unresolved blocker while other tasks progress” check; source inspection alone cannot establish liveness.
- **P4-25 — CONFIRMED.** Assignment records a pending routing row in the actual built-in tool (`assign_task.rs:112-115`; batch equivalent at `assign_tasks_batch.rs:202`), but the only production `record_outcome_auto` caller found is the Tauri status command (`src-tauri/src/commands/task_commands.rs:47-65`). Agent status updates read build evidence but do not record routing outcomes (`update_task_status_tool.rs:149-219`). Thus autonomous recipe completion can bypass outcome learning; the tool-level gap in P4-25 remains.
- **P4-26 — CONFIRMED.** `TaskRouter::suggest_worker` passes every `WorkersDb::list()` row directly to the scorer (`routing/mod.rs:35-46`), and the scorer uses that full vector without filtering system-defined roles (`routing/scorer.rs:19-24,75-109`). `WorkersDb` seeds system Supervisor/QC roles (`db/workers.rs:328-355`) and preserves an `is_system_defined` flag (`:119,196`). A returned implementation recommendation can therefore include a system role unless the runtime data happens not to rank it; the claim is appropriately a “never” invariant and needs a deterministic negative test.
- **P4-27 — REFUTED as worded; preserve only if consolidated into P4-41.** Its “PA-only / reaches tools only via MCP” rationale conflicts with the current in-process builtin registry (`builtin_tools/mod.rs:121-167`) and active P4-41 text that says the MCP rationale is stale. The current live gap is Supervisor-facing availability, not PA-only/MCP registration; P4-41 already owns that reachable-surface question.
- **P4-28 — CONFIRMED.** `unblock_ready_tasks` has one non-test production caller in the Tauri command path (`task_commands.rs:67-83`); repository search found no call from the in-process agent status tool or recipe runner. A task completed by an autonomous worker through that tool path will not execute the dependency-unblock logic or its kick. Keep the consumer-level task and assert autonomous completion to claimable-dependent dispatch.

- **P4-42 — PARTIALLY CONFIRMED; slug/recipe premise stale.** The current QC dispatcher recipe is keyed to the existing worker slug `qc-agent` (`defaults.rs:1973-1975`), and UI status handling kicks `qc-agent` (`src-tauri/src/commands/task_commands.rs:38`); it is not a worker slug named `qc-dispatcher`. - **P4-43 — PARTIALLY CONFIRMED; prose claim overstated for worker-* ticks.** `run_recipe` has a deterministic empty-work short-circuit only for slugs beginning `worker-` (`recipes/runner.rs:128-151`); QC's persistent slug is `qc-agent`, and its 30-second recipe explicitly calls `list_tasks` then replies “Queue empty — idle” (`defaults.rs:1962-1964, 1985-1992`). The Supervisor also has a one-minute schedule and no equivalent early check in the inspected runner. Measure actual idle-tick provider calls and spend; do not assume scheduler cadence is the LLM cadence.
- **P4-44 — CONFIRMED unwired.** The checkpoint finding stands: procedural recall is disabled by default (`tool_executor.rs:104-115`) and retrieval returns early while false (`:137-149`); no production enable call was found.
