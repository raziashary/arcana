### Consumer and compatibility limits

- Canonical text helpers are `db::timestamps::now_rfc3339`, `parse_db_timestamp`, and rusqlite row-boundary `parse_row_timestamp` (`db/timestamps.rs:54-106` and `episodic.rs`/`semantic.rs`/`procedural.rs` reader sites). The parser explicitly accepts legacy SQLite/offset-less forms; this does not make direct lexical SQL order equivalent to instant order.
- Named memory compatibility tests include `production_timeline_and_summary_readers_order_mixed_timestamp_formats_by_instant` (`episodic.rs` around 334), `production_semantic_readers_order_mixed_timestamps_by_instant` (`semantic.rs` around 421), and `production_stats_reads_legacy_and_mixed_timestamps_by_instant` (`recall.rs:717`). These prove their actual reader paths, not every timestamp column.
- Named config/hook tests include `populated_pre_retention_config_upgrade_preserves_hook_logs_for_the_reader` (`config_db.rs:284`), `a_pre_ladder_config_db_is_stamped_without_losing_data` (`:381`), and the leap-year/DST annual hook test above. `legacy_persisted_shell_hook_is_refused_by_production_reader_and_executor` concerns legacy action safety, not timestamp order (`hooks/db.rs:442`).
- Scope is current source/schema ladders and these enumerated consumers. No query of a user config/memory database was performed; no test/build/runtime validation was run. Workspace UI/CLI timestamp display consumers and annual session/worker rollups are outside this inventory and are tracked separately by the parent task.

- Additional audit reader check: `analyze_diff_tool.rs:537-546` counts denied egress rows by `outcome` and `operation`, omitting `occurred_at`; the consent integration test at `egress_consent.rs:433-443` similarly projects operation/outcome and orders by id. This corroborates that the audit timestamp currently has no source-found production temporal consumer.
- The shared timestamp-helper suite also contains `canonical_timestamps_round_trip_a_leap_year_across_offset_extremes` (`db/timestamps.rs:259+`); it validates the helper/parser contract, not a database-specific writer/reader pair.
