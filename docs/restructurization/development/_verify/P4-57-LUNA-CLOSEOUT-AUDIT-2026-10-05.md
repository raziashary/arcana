# P4-57 / TG4-19 timestamp closeout audit — 2026-10-05

Read-only audit of production SQLite timestamp writers and corresponding readers, compared with current tests and evidence. No runtime tests or live-resource access.

- MDP §0.0 says shipped code is the anchor; §0.2 requires additive persistence changes absent an ADR; §0.2e requires named proof; §0.2a–c set audit and owner-reporting constraints. No repository `AGENTS.md` was found by `rg --files -g AGENTS.md`.

## Findings

### Confirmed remaining production defects

1. **Memory stats reject legacy timestamps and select the last row lexically.** `MemoryDb` stores episodic `created_at` as SQLite text; its canonical writer/trigger family includes canonical writes, while existing pre-migration rows can retain SQLite's legacy `YYYY-MM-DD HH:MM:SS` format. `memory::recall::get_stats` reads `SELECT MAX(created_at)` (lexical maximum), then calls `value.parse()` rather than shared `parse_db_timestamp`. A legacy offset-less value therefore fails parsing: the returned `last_updated` becomes `None` and `last_updated_ok=false`, which makes the aggregate stats telemetry partial (`recall.rs:566` and `finish_stats_observation` test around `:697`). Mixed-format `MAX` can also return the wrong represented instant. Evidence: `arcana-core/src/memory/recall.rs:522-553` (especially 529-536); canonical/legacy parser is `arcana-core/src/db/timestamps.rs:54-72`; Memory schema/writer inventory is in `arcana-core/src/memory/db.rs` and `episodic.rs` (inspect at implementation time). `rg` found no `get_stats` timestamp or legacy-read regression; existing recall observability coverage at `recall.rs:690-714` does not assert this behavior.
   - Focused proof needed: use an isolated migrated Memory DB and production episodic insert path/reader with legacy and canonical rows whose lexical order differs from UTC order; assert `get_stats().last_updated` equals the actual latest instant and aggregate telemetry remains successful; also cover only-legacy data. Run on Windows and Linux as part of the cross-platform pair inventory.

2. **RunsDb chronology queries still compare mixed-format timestamps lexically.** Production run writers use `now_rfc3339`, but `runs.started_at` is `TEXT` with no canonicalizing trigger/migration, and legacy persisted values remain readable strings. `recent` says newest first but sorts raw `started_at`; `open_runs` sorts raw ascending; three latest-worker-run readers also sort raw `r.started_at`. Same-day legacy space-form and canonical `T`-form values sort by separator, not instant. Evidence: `arcana-core/src/db/runs.rs:316-329` (schema/index), `:207-230` (`LATEST_WORKER_*`), `:285-287` (`OPEN_RUNS_SQL`), `:1353-1370` (`recent`), and `:26` (`now_rfc3339` import). Existing timestamp test at `:1748-1804` proves canonical operation-journal timestamp readback and legacy journal parsing only; it does not exercise `runs.started_at` mixed-format ordering. MDP evidence currently acknowledges the RunsDb active-operation pair only (TESTING_GATES.md:1079).
   - Focused proof needed: seed production `runs`/`worker_run_state` with legacy noon and canonical 09:00 values plus a reverse-separator case; assert recent/open/latest-worker-tick/owner consumers order by represented instant, and verify populated query plans if expression ordering needs indexes. Exercise writer-to-reader creation as well as legacy rows, on Windows and Linux.

3. **Fleet Chat discards the database's correct mixed-format ordering in its consumer.** `TasksDb::list_recent_worker_messages` orders using `julianday(created_at)` and stable `id` (`arcana-core/src/db/tasks.rs:501-505`, method at `:3108-3123`), but `workerChatStore.hydrate` re-sorts the returned production rows with `created_at.localeCompare` (`src/stores/workerChatStore.ts:82-87`). With legacy SQLite space timestamps mixed with canonical `T` timestamps, this makes the displayed chronological log wrong even though SQL returned the right order. The current task communication proof covers Rust DB API readback only (MDP:2478 / TG4:1124); it does not cover this frontend consumer, and current store code has no `parseDbTimestamp` import.
   - Focused proof needed: preserve/query the production list result through store hydration using same-day legacy noon and canonical 09:00 rows; assert UI state remains chronologically ordered (including deterministic ties). Compare via the shared frontend DB-time parser, not the stored string. Run the timestamp frontend cases in UTC, Asia/Bangkok and America/New_York as the existing timestamp consumer matrix requires.

### Inventory/evidence still incomplete by the governing gate

The source scan confirms canonical SQL `strftime('%Y-%m-%dT%H:%M:%fZ','now')` adoption and legacy-normalizing triggers in several table families, but remaining schemas/consumers are not paired exhaustively in current evidence. Examples requiring explicit writer→reader rows before closure include WorkersDb fields and triggers (`arcana-core/src/db/workers.rs:252-346`), GraphStore timestamps/triggers (`arcana-core/src/graph/schema.rs:62-126`, `store.rs:60-87`), plan-item child timestamps (`arcana-core/src/db/plans.rs:245-365`), configuration tables/trigger defaults (`arcana-core/src/db/config_db.rs:37-161`), annotation timestamps (`arcana-core/src/db/annotations.rs:95-122`), and task child tables/triggers (`arcana-core/src/db/tasks.rs:750-1115, 1236-1364`). This list is source-scan evidence, not a claim that every pair here is defective. Existing READINESS_MATRIX row and its dated follow-ups (lines 56, 412-420) already state these classes and the all-pair cross-platform property inventory remain open.

### Remaining closure condition

This report is a static audit, not a complete per-column inventory: broad source search found additional timestamp columns and call sites, and each must be joined to its actual writer and consumer before the TG4-19 matrix can be marked complete. No tests were run, per dispatch. Keep P4-57/TG4-19 open until the three concrete consumer defects are corrected/proven and a complete DB/table/field writer-reader matrix demonstrates cross-platform round-trip/property coverage at each pair.
