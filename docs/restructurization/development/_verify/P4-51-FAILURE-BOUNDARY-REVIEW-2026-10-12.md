## Findings

### P1 — Cancellation after a partial usage frame releases unknown usage reservations

At [engine.rs:1605](../../../../arcana-core/src/agent/engine.rs), the new cancellation branch drops the provider stream while waiting for later body chunks. Both production budget decorators release their reservations as soon as they see any nonzero `MessageDelta` usage: [run_budget.rs:82](../../../../arcana-core/src/provider/run_budget.rs) takes and settles the full run-token reservation with that partial count, while [capped.rs:189](../../../../arcana-core/src/provider/capped.rs) settles the daily reservation from that frame's cost. Anthropic deliberately emits input-only usage at `message_start`, with output still unknown until `message_delta` ([streaming.rs:177](../../../../arcana-core/src/provider/streaming.rs), [streaming.rs:274](../../../../arcana-core/src/provider/streaming.rs)). If cancellation arrives after that frame but before final usage, the engine preserves reported input but the unknown output is no longer covered by either reservation. The new body-cancellation test only blocks after tool-input chunks without emitting any usage, so it verifies the all-unknown case and misses this partial-known case. Keep the reservation for unresolved usage until terminal usage is known, or otherwise account for the unknown remainder conservatively; add a cancellation-after-input-only-frame case that reads back both ledgers.

### P2 — Biased stream polling can starve cancellation on a continuously-ready body

The changed body loop places `stream.next()` first in a `biased` `tokio::select!` ([engine.rs:1605](../../../../arcana-core/src/agent/engine.rs)). Tokio therefore chooses a ready provider chunk ahead of the cancellation waiter every iteration. If chunks are already buffered or the stream remains continuously ready, the cancellation branch can be postponed until the body drains, so the new path does not promptly stop body consumption as required. Give cancellation priority or check the flag before polling each next chunk, and cover a ready multi-chunk stream with cancellation signaled during consumption.

## Follow-up source review — 2026-10-12

The implementation changed after the initial findings above. The two reported cancellation defects are resolved in the current source:

- **P1 cancellation reservation path:** `RunTokenBudgetProvider::ReservedStream` now accumulates split usage, retains the full reservation through partial frames, settles observed totals only at `Done`/EOF, and charges the conservative maximum on error/drop ([run_budget.rs:75](../../../../arcana-core/src/provider/run_budget.rs), [run_budget.rs:104](../../../../arcana-core/src/provider/run_budget.rs)). `CappedProvider::ReservedStream` follows the same policy ([capped.rs:183](../../../../arcana-core/src/provider/capped.rs), [capped.rs:199](../../../../arcana-core/src/provider/capped.rs)). Both now have input-only-then-cancel tests ([run_budget.rs:469](../../../../arcana-core/src/provider/run_budget.rs), [capped.rs:536](../../../../arcana-core/src/provider/capped.rs)).
- **P2 ready-stream starvation:** the engine now polls the cancellation waiter first in its biased select ([engine.rs:1610](../../../../arcana-core/src/agent/engine.rs)). Its new always-ready fixture signals cancellation during the first poll and asserts that no second chunk is polled ([engine.rs:4351](../../../../arcana-core/src/agent/engine.rs), [engine.rs:4616](../../../../arcana-core/src/agent/engine.rs)).

One adjacent reservation defect remains: both decorators treat every stream EOF as successful completion and settle any accumulated nonzero usage as actual, even if the stream never supplied final usage. In particular, Anthropic emits input-only usage at `message_start` ([streaming.rs:177](../../../../arcana-core/src/provider/streaming.rs)); its adapter turns a clean end of the HTTP byte stream into ordinary stream EOF without checking for `message_delta`/`message_stop` ([anthropic.rs:365](../../../../arcana-core/src/provider/anthropic.rs), [anthropic.rs:370](../../../../arcana-core/src/provider/anthropic.rs)). If that response ends cleanly after `message_start`, `run_budget.rs:124-128` and `capped.rs:220-224` settle only the input tokens/cost and release the reservation for unknown output. Current EOF tests include both input and output frames before EOF ([run_budget.rs:538](../../../../arcana-core/src/provider/run_budget.rs)); they do not exercise EOF after input-only usage. Preserve the reservation maximum unless EOF has a provider completion signal or otherwise proves the usage report is complete, and add input-only-then-EOF coverage for both ledgers.

## Final follow-up — 2026-10-12

The EOF reservation gap is closed in the current source. Both decorators start with `terminal_stop_reason_seen: false` and set it only when `StopReason::parse(provider_id, stop_reason)` is not `Other` ([run_budget.rs:112](../../../../arcana-core/src/provider/run_budget.rs), [capped.rs:201](../../../../arcana-core/src/provider/capped.rs)); empty/unknown reasons therefore do not authorize settlement. Explicit `Done` settles observed usage, while EOF settles observed usage only after a recognized terminal stop reason; otherwise EOF settles unknown usage at the full reservation ([run_budget.rs:124](../../../../arcana-core/src/provider/run_budget.rs), [capped.rs:220](../../../../arcana-core/src/provider/capped.rs)). The new tests cover input-only EOF and unknown-reason EOF for both decorators, along with split usage followed by terminal EOF ([run_budget.rs:538](../../../../arcana-core/src/provider/run_budget.rs), [run_budget.rs:622](../../../../arcana-core/src/provider/run_budget.rs), [capped.rs:747](../../../../arcana-core/src/provider/capped.rs)).

Verdict: the prior cancellation starvation and partial-usage cancellation findings are resolved, and the later premature-EOF reservation finding is also resolved in the reviewed code.
