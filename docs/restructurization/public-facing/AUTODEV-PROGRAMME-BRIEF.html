01 Why restructure

The programme opened with an audit of the shipped code rather than an aspiration. Each finding below was located in the codebase, and each is now closed or scheduled with a test that fails when it regresses.

  • 918 lines of agent code were never compiledPresent on disk, absent from the module graph — a capability the product advertised did not exist in the binary.
  • The /mcp endpoint accepted unauthenticated remote executionRemote code execution on the user's machine.
  • The updater installed unverified payloadsAny tampered update would install.
  • Commands returned raw API keys to the rendererThe user's credentials were reachable from the web layer.
  • CI could not failEvery check carried continue-on-error, so a green build meant nothing.
  • Ten databases had no migration ladderA schema change could silently destroy user data.
  • Secret redaction did not exist in the Rust treeCredentials could reach prompts, logs and permanent memory.

02 Two rollouts

AutoDev ships twice, and the first shipment is not the standalone application.

Rollout 1 — the backend for AutoDesign

AutoDesign is a sister product: a design tool. A design converts to HTML and CSS — which is code, and code is AutoDev's domain. So in Rollout 1, AutoDesign is the front end and AutoDev is the engine behind it. AutoDesign supplies the interface, the file, the user and the approval step; AutoDev supplies the capability.

Four things are delivered: ingestion, turning a PSD or PDF into a structured, editable representation faithful to the original pixel by pixel; fidelity, tooling that measures that faithfulness and refines what falls short; export, back out to a webpage, PDF or PSD; and adaptation and changes — reformatting a design to another size, rebranding it, or changing its content.

Rollout 1 also requires the parts of AutoDev that make those work at all: three conforming model providers with honest cost accounting and a real spend ceiling, a runtime where one failing tool cannot take down the application, working memory, and a fleet.

Rollout 2 — the application

AutoDev standing on its own: its own interface, a compiled code graph for context, a first-run experience, and signed installers for Windows, Linux and macOS.

Rollout 1 is not Rollout 2 with pieces missing

It is a complete product with a different consumer. That distinction is what allows interface work to sit in Rollout 2 without crippling Rollout 1.

03 The plan

Three handovers, not one

M1 — the contract. ✓ Reached on 3 September. PD0 freezes the four operations, publishes the representation that crosses the wire, defines the job and error semantics, and ships an executable reference implementation the AutoDesign team spawns as a child process, plus a conformance suite either side can run. That is enough for them to build and test their entire side while the capability behind it is still being built. It did not wait on the Python removal or on any design phase.

It was closed twice, and the second time is the one that counts. The first closure skipped the two mandatory post-phase audits. When they ran they returned 45 findings, three of which should have blocked it: a task ticked with no deliverable at all, a claim of eight test falsifications against four actually run, and a count off by more than 3× that had already been copied into three governance documents. All 45 were fixed inside the phase rather than deferred. The one that mattered most to the partner team — of the three outcomes the contract freezes, only one could actually be produced, so a consumer could have written a refusal branch that never fired against a documented state no code path could reach. All three have real producers now, proven across a real process boundary, with two new gates to keep it that way.

M2 — the first real capability, about fifteen hours in. After P8 and PD1 a real PSD or PDF becomes a real representation, and the stub starts returning true results. The codebase with the Python subsystem fully removed arrives here, not at M1.

M3 — every design capability live, about thirty hours in. Fidelity, export, adaptation, changes and brand guidelines all live.

At M1 they receive the published contract, a running AutoDev that answers it with working stubs, and a stated execution model — in Rollout 1 the personal assistant performs the design work, and the worker fleet becomes an additional consumer in Rollout 2. Written into the contract rather than left to be inferred.

04 Where we are

P0, P1, P2 and all of P3 are complete. Delivered so far: the security holes closed and gated; an autodev-core crate extracted with zero dependency on the UI framework, letting the desktop app and the command-line tool share one implementation; migration ladders on all ten databases, applied to live data with zero rows lost; secret redaction on the production path; the intermediate representation that everything in Rollout 1 is built on; and now a provider layer that has been tested against the real APIs rather than only against itself.

The estimates were wrong by about 3×, and every phase came in early

Which is exactly why nobody noticed. This page said P2 would take about eleven hours; it took 5h 32m including its audit. P3 A–E: twelve hours estimated, 4h 50m actual. P3-F: seven and a half hours estimated, 1h 58m actual. An estimate that is always beaten never gets challenged, so the figure stayed wrong for three phases while looking like good news.

They have been rebuilt from commit timestamps rather than from judgement. P0 through P3-F is 183 tasks in 21h 23m of working time, across roughly 49 hours of calendar — 8.6 tasks an hour, counting build, tests, automated guards, the independent audits, the remediation those audits caused, and the trackers. Working time is measured as the span between commits with every gap over 45 minutes removed, so it is a floor rather than a flattering number.

The table in §03 plans at a deliberately slower 6 tasks an hour, because a phase’s task list grows when it is checked before building: P2 was written as 27 tasks and became 74, P3 A–E 28 became 43, P3-F 15 became 18. The slower rate carries that growth inside it, and it reproduces the three phases above to within about half an hour each.

Two caveats, stated rather than buried, because a recalibration that is confident everywhere is just the old error wearing a new number. The measured work is all Rust and documentation — the two interface phases, 46 tasks between them, have no measured throughput behind them at all. And the audit overhead, 46% on top of build time, has fallen every phase as the plan improved; these figures assume it stays low, which is an assumption and not a measurement.

What P3 A–E delivered

The runtime phase closed on 2 September: 39 tasks, 19 automated guards, 520 tests. Its headline outcome is that the agent can no longer reach past its own guards. Four of the defects it closed were reachable by the model itself, and none of them appeared in the phase’s task list as written:

  • The permission check did not run at all on tools classified read-only. A tool declaring itself read-only was approved unconditionally in every mode — including the mode whose entire purpose is to ask first.
  • The syntax checker resolved its Python interpreter from the repository being inspected. Cloning a hostile repository and opening a .py file ran that repository’s own binary.
  • The end-to-end probe fetched any URL the model named and returned the response body to it. A cloud metadata endpoint returns credentials.
  • Seven tools that take a file path never checked it against the workspace, two of which acted on the path rather than merely reading it.

They were found because the plan requires an adversarial pass before building and two independent audits after — the same discipline that produced the P2 findings below.

The phase also made the agent’s own accounting honest. A cost ceiling on code review was computed from figures that were hardcoded to zero, so it cancelled itself on every completed review; a provisional charge was taken and never released on eight failure paths, so fifty routine retries could disable review for an hour at no real spend. Both are fixed, and both are guarded by a check that fails if the shape returns.

What P3-F delivered — memory

Memory now depends on what you actually asked. Before this phase every recall returned the same text whatever the question, because the query was never passed to the search. It is scoped to the project it belongs to; it falls back to keyword search on machines that cannot run the embedding model and says so in the prompt rather than silently returning less; and an agent can no longer write into it freely — a gateway decides what is worth keeping and tells the agent which check it failed when it declines.

The audits found four live defects in this phase’s own finished code

That is what the audits are for, and three of the four were reachable by the model itself.

  • The task whose entire purpose is stopping an agent from claiming your authority shipped a flag that let any agent do exactly that — writing a memory at your own confidence, labelled “you told me”, into every repository you open. A comment, a test and an automated gate all asserted this was impossible. All three were written in one sitting from one misreading, so they agreed with each other rather than with the code.
  • Two of the three kinds of memory were never written to the index that recall reads. Every conversation after the upgrade would have been silently unrecallable — and “forget this” did not forget: a memory you removed kept being fed to the model on every turn while every screen reported it deleted.
  • Memory text was placed into the model’s instructions unquoted and last, so a single poisoned file in a repository could have written a standing instruction that survived into every later session, and into every other project.
  • One was in shared safety code: the backup check that guards every database upgrade had been rejecting perfectly good backups since the previous phase, which would have blocked the application from upgrading at all.

All are fixed, each with a test that was deliberately broken first to prove it can fail.

Why readiness is 34% and not 40%

The phase is built and its smoke tests pass, but the specification’s own gate register is not fully satisfied: five of the eight memory gates are not met and three are partly met, verified by an independent reviewer that had not seen any of the reasoning behind the code. The largest remaining item is that the vector-search table is queried by the code and never actually created, so semantic search would fail if it were switched on. It is off by default and nothing is broken today, but the score reflects it. An earlier draft of this figure said 40% and was corrected the same hour — every automated gate written for the phase was green, and that is a fact about those gates, not about the specification they were written against.

What P2 delivered

Prompt caching works and is measured, not asserted: a repeated prompt wrote 11,923 tokens to cache and read back exactly 11,923. That matters because caching is the one optimisation that fails completely silently — below a model’s minimum length, or after a single changed byte, the provider caches nothing, returns no error, and the only symptom is the bill. So the alarm that detects a broken cache was built and proven before the caching it watches.

Spending is now bounded in a way that survives contact with a user. The daily ceiling previously lived only in memory, so it reset to zero every time the application was reopened — a per-session limit describing itself as a daily one. Two models were on offer that could not be priced at all, and therefore billed as free and ran past any ceiling; they have been withdrawn until a verified price exists.

What only a live test could find

The phase wrote 27 tests against captured provider payloads, all passing. A deliberate, credential-gated test against the live APIs then found five defects that those tests could not have caught, because a captured payload freezes the vendor’s behaviour at the moment it was recorded and goes on passing afterwards regardless:

  • A model in the picker did not exist. Google returns “not found” for it; the identifier it actually ships under differs.
  • Google had changed its tool-calling contract. It now rejects any repeated tool call that omits a token it issues itself — which broke every multi-step tool conversation on Gemini, the provider chosen as primary for the first rollout.
  • Five preconfigured agents were pinned to models withdrawn in February 2026, including the default every new agent inherits.
  • A component that reviews code changes could never have worked: it read its model from two environment variables nothing sets, then fell back to a name that has never existed at any provider.
  • A token estimate erred in the opposite direction to its own documentation, which would have made the new cache alarm raise false alarms.

None of these failed to compile, and none failed a test. They are the reason the live check now runs at every phase closeout.

What the mandatory audit found after that

Every phase closes with an independent review by people — here, agents — who have not seen the reasoning behind the work. P2 passed its own tests first: 74 tasks, 12 smoke checks, 11 automated guards, all green. The audit then found four defects that would each have reached users:

  • Every streamed conversation with Anthropic was billed at double its real cost. The provider reports usage cumulatively and repeats it across two messages; we were adding both. Settled by capturing the raw network traffic, because two comments in our own code claimed opposite things.
  • The application carried API keys in its process environment, where any command the AI itself chose to run could read them.
  • The daily spending limit recorded nothing on the runs that spent most — including, precisely, the runs that stopped because they ran out of budget.
  • Keys for the primary provider could not be saved at all, because the check that validates a key pointed at a model that had been withdrawn.

None of them failed to compile. None of them failed a test. Three were inside code written to prevent exactly that kind of failure. Sixteen findings were fixed and locked behind new automated guards; six are recorded as open with the reason stated rather than quietly closed.

P1 built 22 tasks in 2 hours 50 minutes; its audit and the resulting fixes took a further 3 hours 30 minutes. P2 grew from 27 tasks to 74 as its pre-build audit and live testing surfaced work that had not been visible when the phase was planned, and its own audit added roughly a third again. The estimates above carry that cost rather than omitting it — it is the reason the figures are worth reading.

05 How the work is governed

The discipline is the reason the estimates are worth anything.

Evidence classes

No task is complete without a named proof recorded against it — unit-proven, live-database-proven, smoke-proven, gate-proven, benchmark-proven. "It should work" is not a status.

Falsification

A test that has never been seen to fail is not trusted. A violation is deliberately introduced, the check is confirmed to catch it, and the violation is removed.

Mandatory post-phase audit

Every phase ends with independent auditors reviewing the work against the evidence. This is not a formality.

What P1's audit found

It returned 116 findings and established that the phase's headline claim was false: secret redaction had been wired to a function that nothing in production called, so it protected nothing while two separate proofs reported green. It was found, fixed, re-proven, and recorded — including why both proofs had been able to pass over unprotected code.

A learnings register, with running counts

Recurring mistakes are tracked by class and counted, on the principle that a repeat is worse than a novel error. Every architectural decision is logged as it is made — what, why, when, where and how — including retractions when a previous finding proves wrong.

07 In one paragraph

AutoDev is being rebuilt to a standard where every claim is backed by a test that can fail. Four phases are complete and independently audited, including the runtime phase that closed four ways the agent could reach past its own guards. The next milestone is a working backend that turns designs into faithful, editable, adaptable code — handed to the AutoDesign team roughly 37 working hours from now, with a published contract and a spawnable reference implementation so they can build in parallel. Full capability follows at roughly 92 hours, and the standalone application at roughly 127.
