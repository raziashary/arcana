## PART 2: MODULE NARRATIVES

### skills

The module loads `.md` workflow templates with YAML frontmatter from `~/.autodev/skills/{category}/`, indexes them in memory, validates parameters, and renders `{{param}}` substitutions into a prompt the PA or a Fleet worker can execute. The plumbing is real and end-to-end: `main.rs:92-102` seeds defaults and reloads the registry, `main.rs:496-503` starts the file watcher, `commands/skill_commands.rs` exposes eight commands, and the frontend consumes them (`src/stores/skillStore.ts`, `src/tabs/Chat.tsx:380`). **Unlike hooks and plugins, skills genuinely work.**

The headline defect is that the rendering engine does not implement the template language the shipped skills are written in. `skills/engine.rs:82-84` is a flat `String::replace` loop, while five of the sixteen default skills contain `{{#if}}/{{else}}/{{/if}}` blocks. Every invocation of `/feature-implementation`, `/api-endpoint`, `/database-migration`, `/dependency-update`, or `/browser-test` emits raw handlebars markup and *both* branches into the agent's prompt (SK-59). Second, `is_builtin_path` is a constant `true` so every skill — including a user's own — is flagged built-in (SK-58). Third, `ensure_default_skills` rewrites all sixteen files on every launch with no backup, so any user edit is silently destroyed at restart (SK-69).

### recipes

Recipes are YAML worker definitions in `~/.autodev/recipes/`; `RecipeScheduler` spawns one tokio task per bound worker that fires `RecipeRunner::run_recipe` on a cron, dispatching either to the core-orchestrator LivingAgent (Mode 2) or the in-process Rust `AgentEngine` (Mode 1). The machinery does run (`main.rs:299`, `:305`, `:471-488`).

**It also contains the worst bug in this audit.** The cron loop's status gate at `scheduler.rs:227` only fires for `idle`, `active`, and `error`; anything else falls to the `_` arm at `:277`, which logs and skips. But `run_recipe` writes two statuses that are not in that list — `fallback_idle` (`runner.rs:594`) and `mode1_idle_no_provider` (`:625`). Since every recipe except `worker-cleanup` is `FallbackPolicy::Mode2Only`, the moment the orchestrator becomes unreachable after having once been healthy, **every worker latches into `fallback_idle` and its cron loop never fires again** — not even after the orchestrator recovers (SK-01). Adjacent, `:220` collapses a `WorkersDb` error to `None`, which matches the `paused/deleted` arm that `break`s the loop: a single transient SQLite lock permanently terminates a worker's schedule (SK-02).

**These two are the traced mechanism of BUG-ASSIGN (owner's bug #3).**

The Fix-8c sentinel build guard is unreachable: `reconcile_stranded_task` at `:482` promotes every `InProgress` task to `qc_review` before `guard_and_validate` at `:485` looks for one, so it always returns at `:891` (SK-27) — and even if reached, `Ecosystem::install_cmd()`/`validate_cmd()` are only interpolated into a log note, never executed (SK-26).

**The most damaging content defect is BUG-COMPILE (owner's bug #1), and it is SK-50.** Every worker recipe mandates `bash('<cmd> 2>&1 | tee build.log; echo "EXIT:$?"')`, the bash tool runs `cmd /C` on Windows (`agent/builtin_tools/bash.rs:89-92`), and `update_task_status` hard-rejects `qc_review` without recorded successful build evidence (`agent/builtin_tools/update_task_status_tool.rs:141-152`). **On Windows no worker can ever produce that evidence, so no task can ever reach QC.** The recipe text at `defaults.rs:181` even acknowledges the bash tool uses cmd.exe on Windows while prescribing sh syntax throughout.

### hooks

**Hooks do fire** — `HookRegistry::fire` has 19 call sites across `agent/engine.rs`, `agent/tool_executor.rs:139/179/365/406`, the file tools, `agent/builtin_tools/update_task_status_tool.rs:272`, and `commands/session_commands.rs:53/86`. That is not the defect.

The defect is that **half the hook surface is a writer with no reader**. Fifteen of the thirty types have zero emitters: all five git types, all five plan types, `on_qc_approve`/`on_qc_fail`, `on_permission_request`, `pre_file_delete`, and both checkpoint types. All fifteen are offered in the settings dropdown, documented as working in the info modal, and `pre_commit` — a dead type — is the Add-Hook form's default. **The most likely first hook a user creates is guaranteed never to fire** (SK-06). Three of the eight actions are equally hollow: `Script` and `Modify` return `Skipped`; `EmitEvent` and `Notification` return `Executed` while doing nothing.

The parts that do run are unsafe: fail-open on DB error (SK-03), corrupt-conditions-default-to-match-all plus corrupt-action-defaults-to-Block (SK-04/SK-05), invalid globs and regexes silently skipped rather than rejected (SK-15), shell injection through LLM-controlled `{{file_path}}` (SK-12), orphaned processes on timeout (SK-07), an unbounded HTTP call awaited inline before every tool (SK-08), and on Windows `file_pattern` can never match because `glob::Pattern` treats backslashes as escapes (SK-14).

### plugin

**`plugin/token.rs` implements nothing that gates plugin execution.** It is a standalone HMAC-signed setup-token issuer for worker enrollment, reachable only via `generate_setup_token`/`validate_setup_token`; no install, run, or uninstall path consults it. There is no sandbox, no allowlist, no signature verification, no privilege reduction, and no confirmation anywhere in the module.

The result is arbitrary code execution by design (SK-90). `install_plugin_from_yaml(yaml)` takes a manifest from the frontend and hands `commands.install.<os>` to `cmd /C` / `sh -c` with the desktop user's full privileges. None of these have a timeout (SK-89) and all block a tokio runtime thread (SK-88). Compounding this, `plugin_install_dir` is an unsanitised `join` on the plugin name (SK-83/SK-91).

The token module's own security is broken independently: `random_bytes` is an LCG seeded from `unix_now() ^ pid`, making every fleet secret forgeable (SK-76). And the built-in catalogue is hazardous — `worker-backend`'s uninstall is `rustup self uninstall -y`, which removes the user's entire system Rust toolchain when they uninstall *or update* an AutoDev plugin (SK-99), and `update()` runs that uninstall before attempting an install with no rollback (SK-85).
