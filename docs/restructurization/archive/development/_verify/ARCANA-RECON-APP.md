- Primary state root is created as `$USERPROFILE/.autodev` or `$HOME/.autodev` (`autodev-core/src/db/mod.rs:72-81`); databases include tasks/config/workers and session `autodev.db`. OS keyring service is the literal `autodev`; fallback vault label points to `~/.autodev/config/vault.enc` (`autodev-core/src/vault/keychain.rs:21,48`). No credential contents were accessed.
- `src/stores/agentStore.ts` subscribes to session-filtered `agent:token`, `agent:tool-start`, `agent:tool-end`, permission and terminal events. `src-tauri/src/commands/agent_commands.rs:80` loads provider/model, vault key and stored session; saves the user message; builds prior history; constructs shared factory provider and `AgentEngine` in a background task. PA mode is separate from permission mode; interactive engine uses ManualApproval.
- The restructure vision is historical design context, not current capability evidence: its master thesis describes sidecars, while live source already links the shared Rust runtime. Every remaining gap must be rechecked against source.

- Interactive entry: `src/tabs/Chat.tsx:306` invokes `send_message`; cancel uses `cancel_agent` at line 322. `AnnotationModal.tsx:128` is another entry. `src-tauri/src/commands/agent_commands.rs:201-310` builds the provider and engine, applies the resolved PA mode and explicit interactive permission policy, and runs with stored history. `agent_commands.rs:334-397` persists new assistant messages and tool-use structure from returned history.
- Shared runtime: `autodev-core/src/agent/engine.rs:193-252` composes stable instructions and query/repository-scoped memory, then advertises the mode-filtered registry. Around lines 550-585 it builds and streams provider requests. Around lines 770-830 it appends assistant output, stops when no tool calls remain, resolves registered tools and executes a batch. Read tools may run concurrently; write tools run serially through the executor.
- Providers: `autodev-core/src/provider/factory.rs:34-45` explicitly supports Anthropic, OpenAI and Google, rejecting other IDs and wrapping requests in the daily ceiling. The recipe runner still has its own three-provider match and explicit capped wrapper (`recipes/runner.rs:276-292`), so the factory comment claiming one construction point is broader than the current implementation.
- Context: `autodev-core/src/agent/context.rs:93-129` reads global/repository instructions from SQLite first, then falls back to `~/.autodev/config/autodev_global.md` and `<repo>/.autodev/autodev.md`. `build_agent_stable_prompt` at line 157 composes invariant core, role instructions, then user instructions; `memory_block` at line 226 invokes memory retrieval with session, query and repository. The recipe override path also calls this composer and memory in `engine.rs:235-236`.
- Fleet: `autodev-core/src/recipes/scheduler.rs:104-141,248-251` drives startup and cron ticks; `kick_worker` at line 494 calls the same runner for immediate push dispatch. `runner.rs:96-355` refuses unattended recipes needing interactive prompts, skips taskless `worker-*` ticks, resolves model from worker/recipe/active/default, resolves shared workspace or `~/.autodev/agents/<slug>`, obtains a configured provider, creates a native engine with worker identity and recipe permission mode, applies a default worker budget, and emits tick events around the native run. Recipe sessions are ephemeral rather than inserted into the session store.
- Task board reader: `src/stores/taskStore.ts:235-242` listens for `task:changed` and refetches via IPC; `src-tauri/src/commands/task_commands.rs` owns UI board commands and status-edit/unblocked-task dispatch. This is a real UI reader, not only a task writer.
- CLI limitation: `src-cli/src/main.rs:57-107` exposes tasks, workers, config, plans, system, analytics, logs, plugins, worker setup and REPL. There is no agent run verb. `src-cli/src/commands/mod.rs:1-7` records its retirement because it depended on deleted HTTP orchestration. Linking `autodev-core` does not mean the executable currently exposes agent execution.

## Product boundary and source-versus-plan caution

The older `docs/development/DEVELOPMENT_PLAN.md` explicitly labels itself superseded in part and delegates authority to the restructure set. The master restructure vision describes a single-user, single-machine local-first app (section 1.5), but also retains broader design/adaptation work. Owner clarification during this reconnaissance: retire the PD0 design contract and start Arcana with fresh local data. That clarification replaces the need to choose whether old AutoDev data should migrate; it does not itself specify every installer, CLI or external integration compatibility policy.

Capabilities above are source-confirmed wiring, not a fresh runtime certification: no app launch, tests, network or credential reads were authorized for this subtask. The graph vision's PLANNED label and historical defect statements must not be treated as live failures without further tracing. Current source has tree-sitter/petgraph dependencies and graph modules/tools on disk; graph consumption and scope-selection completion were not conclusively established in this bounded pass.

## Additional live-source correction

`autodev-core/src/agent/builtin_tools/mod.rs:12-13` DOES declare `graph_prompts` and `graph_tools` now, contrary to historical vision defect M-17. However, its full `register_for_mode` body (line 108 to EOF) registers no graph tools in either PA branch. FastDevelopment and Review share file, execution, task, memory, subagent, review, budget and coordination tools. Delegate registers only create_task, planner and memory tools. Therefore module compilation is confirmed; default engine graph-tool availability is not present in this registry. Automatic graph-guided context selection also was not observed in the context composer. This is a bounded source observation, not a new implementation recommendation.
