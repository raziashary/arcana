# P4-61 guarded copyback wiring review — 2026-10-12

Read-only source review of the Linux smoke/cgroup candidate, descriptor-relative staging planner, current workspace write lease, and their live consumers. This report is the only file changed for this task. No source, Git state, build, quota run, credential, network, or machine configuration was touched. The already completed quota proof is referenced from `P4-61-DELEGATED-QUOTA-PROOF-2026-10-12.md`; it was not rerun.

The owner-approved boundary is ADR-LOG-RESTRUCT-0359, with implementation constraints refined by ADR-LOG-RESTRUCT-0349, ADR-LOG-RESTRUCT-0363, ADR-LOG-RESTRUCT-0365, the post-failure copyback policy in ADR-LOG-RESTRUCT-0235, and the earlier sandbox-owned staging ADR-LOG-RESTRUCT-0171. Owner approval permits guarded staging/copyback; it does not establish a production consumer or close P4-61/TG4-31.

## Source-grounded current state

- `arcana-core/src/platform/process_sandbox/linux_smoke.rs` is compiled only under `cfg(all(test, target_os = "linux"))` in `process_sandbox/mod.rs`. It contains a candidate helper/cgroup runner and the quota proof, but no calls to `snapshot_to_stage` or `plan_copy_back`, no tmpfs mount, and no production caller. Its `LinuxLoopbackChild` comment explicitly says a consumer must integrate it behind `SandboxedChild`.
- The current production Linux implementation is a separate path: `process_sandbox::spawn` in `arcana-core/src/platform/process_sandbox/mod.rs` starts a direct `tokio_process::Command`, applies `linux::confine`, and returns `SandboxedChild::Tokio`. `SandboxedChild::wait` waits for that child PID; its `Drop` sends SIGKILL to the process group. This path does not own a delegated cgroup lease, stage, or copyback plan.
- The actual typed-command consumer is `ProjectCommandTool` in `arcana-core/src/agent/builtin_tools/project_command.rs`: it calls `process_sandbox::spawn`, captures output, awaits `child.wait`, then returns `ProcessOutput` for BuildEvidence/QC handling. Bash also calls `process_sandbox::spawn`. They are the relevant production paths to route through a proved stage-aware runner; a staging unit test or an uncalled helper is not integration proof.
- `WorkspaceWriteLease` exists in `arcana-core/src/platform/workspace_write.rs`. It is a cross-process OS file lock keyed by canonical workspace identity, uses retained lock files in Arcana-owned storage, polls with a 30-second bound, and releases on drop/cancellation. Its source comment correctly says it coordinates managed writers but cannot stop external editors.
- `ToolExecutor::acquire_write_lease` currently acquires that lease only when `effect_for_input(...) == ToolEffect::Write`; the batch handler retains it over handler execution and journaling. `ProjectCommandTool` reports `ToolEffect::Execute` for build/test/lint/run (install is `HostApproval`), and Bash reports `FreeformShell`. Therefore the current lease path does not serialize copyback for those subprocesses. The integrator must resolve lease admission/lifetime for staged execute and shell paths without double-locking or bypassing the shared lease. ToolExecutor and shell-hook routing are owned by other workers; this report does not prescribe their API changes.
- `linux_smoke/staging.rs` currently offers `snapshot_to_stage` and `plan_copy_back` only. The snapshot copies bounded ordinary files/directories, records identities/digests, preserves executable mode while stripping set-id bits, and rejects symlinks, multiply-linked files, special files, and quota overflow. The planner compares baseline, current host, and staged trees, emits create/write/delete changes with staged digest/size, checks root identity and the changed path plus parent chain, and leaves the original untouched. Its tests prove planning and conflict rejection, not host mutation.
- `ChangePlan` contains paths, kinds, digests, sizes, and totals; it contains neither staged bytes nor a pinned stage descriptor. There is no apply function, atomic replacement helper, displacement store, per-file durable transaction record, or restart recovery path in the reviewed files. The existing plan's doc comment intentionally says apply is unavailable until a caller can serialize writes.
- There is no tmpfs mount setup in the Linux candidate or staging module. `helper_main` unshares only user and network namespaces. It validates an absolute workspace path, and `run_confined_child` grants Landlock `LL_ALL` to that workspace; the stage can be used as this workspace only after a caller prepares it and maps the requested cwd into it. The child seccomp filter denies namespace changes, including `CLONE_NEWNS`. Current ordinary-temp staging tests do not prove bounded private tmpfs or stage persistence.
- `LinuxLoopbackChild::wait` waits for the helper, stops the forwarder, kills the helper process group, then calls aggregate `cgroup.kill` and waits for `populated=0` before removing the tree and returning the observed exit code. That is a candidate success-path stop barrier. Its `Drop` path is best-effort and discards errors; current ProjectCommand timeout handling drops the child. Copyback on timeout/cancellation therefore needs an explicit stop/reap operation that returns confirmed tree-empty evidence before apply, rather than relying on `Drop`.

One planner behavior needs a focused correction/proof: `Identity` includes directory size, mtime, and ctime, while `plan_copy_back` compares the complete current root identity to the baseline before checking individual changed paths. A benign unrelated top-level file addition/removal changes root metadata and is therefore reported as “workspace root was replaced,” despite `compare_trees` saying unrelated concurrent host edits do not conflict. Root identity replacement should be distinguished from mutable root metadata, then per-path and parent checks should determine conflicts. Preserve fail-closed behavior for actual root replacement.

## Minimal wiring sequence

1. **Select the real consumer and hold one workspace lease.** Route the actual ProjectCommand (and any approved shell path) through a host-owned staged-run object. Acquire the same managed workspace lease before its operation journal/side effect and retain it through child creation, stop confirmation, planning, apply/recovery receipt, and stage cleanup. Existing `ToolEffect::Execute`/`FreeformShell` classification means today’s `ToolEffect::Write`-only admission does not do this; parent integration must settle the scope and avoid reentrant acquisition.
2. **Give the stage an owner and lifetime outside the helper.** Create an exclusive bounded tmpfs stage in a dedicated host-controlled mount namespace or equivalent owned mount lifetime. The process that owns the stage must remain alive and retain root descriptors after the helper exits. The helper currently creates only user/network namespaces and dies before `LinuxLoopbackChild::wait` returns; stage bytes in a helper-owned mount namespace would disappear with it. Do not mount tmpfs into the ordinary host mount namespace or assume a path in the helper survives helper teardown. Snapshot the selected canonical workspace into the stage, retain its baseline and stage authority, map cwd relative to the workspace, and pass the stage root (not the host root) to Landlock and the child.
3. **Return a stop barrier on every outcome.** Preserve exit code, timeout, and cancellation as separate observed outcomes. On success, nonzero exit, timeout, or cancellation, kill/reap descendants and wait for the aggregate cgroup to report empty before planning. Keep the stage owner/mount and all staged bytes alive at this point. If stop cannot be confirmed, refuse copyback and retain recoverable state.
4. **Plan against fresh host state under the lease.** Reopen/pin host and stage roots without following links; verify workspace identity, entry/byte quotas, allowed file kinds, and staged digests. Detect path and parent conflicts. On any conflict, mutate no host paths; preserve both the stage and displaced host version for recovery. Unrelated host edits should remain intact and should not be mislabeled as root replacement.
5. **Apply as a recoverable sequence of atomic per-path replacements.** Before changing a path, durably record workspace/run identity, expected baseline and staged digest, destination, displacement backup, and progress. Stage each replacement beside its destination using descriptor-relative operations; bound and hash while copying staged bytes, set safe mode, and fsync the temp and parent. Displace an existing host file into a recoverable same-filesystem backup without overwriting an unexpected path, revalidate the displaced identity, then atomically install the staged temp. Record each completed step durably. Keep backup and stage bytes until a durable commit/recovery receipt is recorded. A multi-file workspace change is not one filesystem-atomic operation; recovery must resume or roll back each recorded item without losing either version.
6. **Keep build evidence independent from copyback.** Per ADR-LOG-RESTRUCT-0235, perform conflict-free apply after success, nonzero exit, timeout, or cancellation, as enabled by the owner-approved ADR-0359 direction, but retain the original exit/incomplete classification. A copied change cannot turn a failed/incomplete build into passing QC. Surface copyback conflict/recovery as its own outcome; cleanup the tmpfs only after successful durable commit or an explicit recoverable handoff.

The existing descriptor-relative pieces to reuse are `open_root`, `open_at_directory`, `mkdir_open_at_directory`, `dup_fd`, `directory_names`, `identity_fd`, and the `openat`/`fstatat(AT_SYMLINK_NOFOLLOW)` scan path in `staging.rs`. No reviewed helper applies a `PlannedChange`, performs an atomic rename, journals displaced bytes, or safely removes a destination. The copyback implementation should remain descriptor-relative from pinned host/stage roots and must not turn a planned relative path into an unchecked absolute write.

## Behavior proof required before capability integration

- Drive the actual registered ProjectCommand handler through a staged Linux launcher. Prove a successful build output reaches the selected host workspace, and nonzero, timeout, and cancellation still preserve their observed process classification while conflict-free changes are returned only after every descendant is stopped.
- Use a child that forks a delayed writer. Assert host apply starts only after the writer is dead and the cgroup reports `populated=0`; cancellation/drop must use the same explicit stop barrier.
- In one real-consumer fixture, modify/create/delete staged files while an external fixture edits the same host files. Assert no conflicted host edit is overwritten, the staged version and displaced host version remain recoverable, unrelated host edits survive, and a changed workspace root is rejected. Include the benign unrelated top-level edit case to catch the root-identity metadata issue above.
- Inject failures/crashes before displacement, after displacement, after atomic install, and before receipt commit. Reopen the durable journal and prove recovery finds the staged bytes and displaced bytes, does not duplicate/lose an update, and cleans only after a terminal recovery receipt.
- Mount a size/inode-limited tmpfs in the owned stage namespace, write from the confined descendant, stop/remove the helper, then prove the host-side stage owner can still read/plan/apply those exact bytes. Finally unmount the owned tmpfs and verify no mount, stage directory, cgroup, child process, or listener remains. Also prove denied symlink/traversal/special-file output and byte/entry overflow fail closed.
- Read back the production operation journal and final host contents, not just helper return status or a successful plan. Verify QC refuses nonzero, timed-out, cancelled, conflicted, incomplete, or unresolved-recovery commands.

## Planner regression follow-up — 2026-10-12

The earlier finding that unrelated top-level edits looked like root replacement is corrected in the Linux candidate planner. Root replacement now compares stable directory identity and access mode while ignoring mutable size, link-count, and timestamps. Existing parent-chain checks use the same stable directory comparison; the exact changed file still uses its full captured identity, and parent/root permission or type changes remain conflicts.

The regression creates a staged edit to parent/managed.txt while the host adds an unrelated file both within that parent and at workspace root. The planner succeeds with exactly one proposed change and preserves both host-added files. A separate regression renames the snapshotted root, creates a replacement with matching file contents, and confirms planning refuses it. Existing concurrent-target-edit and parent-substitution cases remain covered.
