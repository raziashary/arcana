## Bounded loopback path and limits

- First wiring step is clear: route each model-authored start command through `ProcessSpec`/`process_sandbox::spawn`, preserving argv as shell invocation, selected workspace cwd, credential scrubbing, bounded timeout/output, and descendant teardown. This reuses the shared OS boundary and keeps filesystem policy in the sandbox owner. This alone makes the current probe nonfunctional because that boundary intentionally denies networking.
- A capability must be represented in `ProcessSpec`/per-run sandbox policy and be derived from a host-approved bounded request (at minimum exact loopback address, selected port(s), protocol, lifetime, and which child processes receive it). No such field, request, or approval payload exists today. Reusing `Execute` would skip prompting in Autonomous; reusing `HostApproval` would prompt there but its declared meaning is installation, so its consent text/contract does not fit this capability. Exact approval wording/data binding is an owner/API choice.
- Linux seccomp currently filters syscall numbers and the socket domain; it cannot inspect the user-memory sockaddr contents to allow only a chosen loopback address/port. A broad allow for socket/bind/connect would violate the preserved outbound denial. No network namespace, broker, cgroup/BPF endpoint policy, or inherited listener capability appears in the shared sandbox source. A Linux-specific enforcement mechanism therefore needs an architectural choice and separate proof before capability enablement; there is no exact existing implementation path to point at.
- Windows SBOX production policy can only express deny-all egress in this checked-in subset. PSEC's schema can express endpoint/port rules and host-loopback ingress, but current production generic path uses SBOX and PSEC policy construction denies all egress; whether a PSEC policy can implement the requested server direction and is supported on every target build is unproven. Switching policy/API is a platform architecture choice and needs real host-version proof. Keep SBOX deny-all unless that proof exists.
- macOS has no child execution path yet. The current service is readiness-only; no network entitlement, process policy, staging authority, or host↔child loopback behavior is implemented/proven. The macOS runner's entitlement and network enforcement design must be approved and proven independently.
- Do not enable the capability on any OS until the production child can prove selected-workspace access, denial of sibling/user-file reads, denial of external egress, denial of loopback outside the approved bound, successful approved local server startup/probe, and descendant teardown. Existing Linux and Windows focused deny tests are evidence for today's deny-all behavior only; they do not prove the new exception. TG4-31 and P4-61 remain open in the current plans.
