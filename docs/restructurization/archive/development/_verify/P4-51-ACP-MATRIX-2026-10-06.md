## Implemented bounded ACP matrix

Added `acp_matrix_tests::acp_live_fastdevelopment_registry_has_success_and_failure_proof` only in the `cfg(test)` area of `send_worker_message.rs`. It creates the real FastDevelopment registry, asserts the nine requested registrations, retrieves each concrete tool from that registry, and calls it through `ToolExecutor::execute_batch` under one isolated temporary home/workspace with supervisor/worker identities, stable task/run/session/call correlation, and no external services.

Covered success plus a tool-specific failure for all nine requested tools:

| Tool | Success and readback | Failure |
| --- | --- | --- |
| `send_worker_message` | Persists message; reads row and routes to actual registered worker | Temporary SQLite insert trigger with a planted body value and overlong/private database diagnostic; also unknown-recipient validation |
| `list_worker_messages` | Worker reads real message; durable row transitions to `read` | Tasks DB obstruction inside temporary home |
| `list_stale_worker_messages` | Ages the fixture row and returns it from the Supervisor stale reader | Worker-role refusal; temporary Tasks DB obstruction |
| `list_worker_health` | Returns the registered fixture worker and its durable run ID | Worker-role refusal |
| `acknowledge_worker_message` | Acknowledges and rereads durable `acknowledged` state | Temporary SQLite update trigger; also invalid ID |
| `list_worker_requests` | Reads the actual request created by the worker tool | Temporary Tasks DB obstruction |
| `resolve_worker_request` | Resolves listed request and rereads durable `completed` status | Temporary SQLite update trigger plus a planted note; also invalid action |
| `request_supervisor_action` | Creates request which `list_worker_requests` consumes | Temporary SQLite insert trigger plus planted payload; also invalid request type |
| `reconcile_worker_operation` | Resolves a real journal intent as Supervisor and rereads actor/state | Temporary SQLite reconciliation trigger with planted journal detail |

For every failure, the test checks `is_error`, bounded JSON output, `schema_version`, `ok=false`, error code/category, operation/tool identity, bounded message/cause/action, retry fields, available session/agent/task/run/call correlation, timestamp, and planted-value absence where applicable. Successes check actual result JSON and durable writes/readbacks. The success and failure inputs use unique call IDs that are asserted against the executor-returned ID and envelope context.
