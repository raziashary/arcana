- Root cause confirmed in `ToolResult::error_with_next_step` (`tool_trait.rs`, lines 41-77): it redacts, replaces controls, and takes the first 512 characters of the message before an input-aware sanitizer receives it. `ReadFileTool::execute` constructs `Cannot read '<path>': {e}` (read_file.rs, around line 142), so a long path comes first and pushes the useful OS cause beyond that 512-character cut.
- The later input-aware sanitizer (`tool_trait.rs::sanitize_tool_error`, lines 396-440) recursively collects input strings and removes an argument only when the complete value occurs (or exact equality for values shorter than 12 chars). `ToolExecutor::execute_batch` passes `Some(&input)` to `with_execution_context_and_input` (tool_executor.rs, around lines 858 and 1144); therefore the current sanitizer sees the raw long input but only the already-truncated path prefix in `cause`, which fails the complete-value match.
- The all-47 engine matrix (`engine.rs::builtin_handler_failures_reach_model_as_correlated_private_error_results`, around lines 2795-2810, 2860-2870, 3090-3145) now correctly uses a 1,049-character absent path, confirms a real `std::fs::read_to_string` OS error exists, routes `read_file` through the registered executor, and asserts the planted OS-path marker is absent. The reported regression is consistent with the sanitizer’s full-value-only match. It also bounds cause/message to 512 characters and full model content to 8 KiB; it does not currently require the model cause to retain the actual OS error explanation.
- Minimal sanitizer correction proposal: preserve the current exact-match replacement, and additionally detect a sufficiently long (at least the existing 12-character threshold) reflected prefix of each input string in the already-redacted cause/suggested-action/path value. Replace the longest such prefix with `[argument omitted]`, processing longer arguments first as today; implement the match using Unicode scalar boundaries (never byte slicing). This directly closes the observed first-512-character partial-path reflection without redacting short/common fragments or unrelated error text.
- Important limitation: that matcher alone can hide the leaked prefix, but it cannot recover an OS cause already removed by `ToolResult::error`'s earlier 512-character head truncation. The actual `read_file` formatting puts the long path before `{e}`. To meet useful-cause retention for this exact case, either move the final 512-character bound until after input-aware sanitization (with a separately bounded intermediate error representation), or change this producer's error wording so the concise OS cause precedes/does not echo the path. The smaller source change is cause-first wording in `read_file`; the more general fix needs an explicit bounded intermediate policy. Do not claim cause retention from a `sanitize_tool_error`-only patch.
