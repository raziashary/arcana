## Findings and next slice (2026-10-09)

1. **Implementation absent in tracked and visible files.** Repository-wide filename/content searches find no `.xpc` product, XPC service source, service plist/entitlements, build target, helper signing step, or XPC consumer. `process_sandbox/mod.rs::spawn` remains an unconditional macOS `Unsupported` refusal. The dirty/untracked inventory contains no runner-related path; the earlier accepted ADR-0170 explicitly recorded the same absence.
2. **The production abstraction already has the right consumer boundary.** `ProjectCommandTool` and `BashTool` both call `process_sandbox::spawn`; its `SandboxedChild` contract supplies bounded stdout/stderr reads, `wait`, and Unix process-group cancellation. The macOS adapter must fit that contract so CLI and desktop worker invocations share it.
3. **The CLI/Tauri process entrypoints are not current helper owners.** Both invoke the shared bridge dispatch before normal startup, but `run_bridge_entrypoint` dispatches only on Windows and returns `None` elsewhere. Keep the new XPC service distinct from the Arcana CLI/desktop executable unless a concrete implementation requires otherwise.
4. **Tauri bundle is the packaging owner today.** `src-tauri/tauri.conf.json` lists no resources; `installers/dmg/create-dmg.sh` runs `npm run tauri -- build --bundles dmg`, then optionally signs the already-built app recursively/deep. There is no step to build/embed/sign a nested XPC product before signing Arcana.app. `scripts/build-macos.sh` is only a wrapper for that DMG release flow, with optional upload credentials; it does not supply a non-secret CI helper build path.
5. **CI consumer already exists.** `.github/workflows/ci.yml::build-smoke` has a macos-14 job and invokes the existing exact TG4-18 production Rust/Node/Python launcher corpus after setup. Windows alone builds `arcanactl` first for its bridge. Once the XPC runner is packaged, the macOS job should build/package the helper before that corpus and then let the existing test prove the real consumer path; no parallel corpus should be invented. Its current working-tree edit is the unrelated P4-39 budget-resolution step (verified from `git diff`).
6. **Policy ownership is adequate; build mechanics are not specified.** Core P4-11 and TG4-18 require real platform launcher proof; P4-61/TG4-31 additionally require external-read/network denial, exact runtime, descendants, approval, staging and structured refusal evidence. ADR-0170 approves the separately signed App Sandbox XPC architecture; ADR-0171 approves guarded sandbox-owned workspace staging/copy-back; ADR-0175 requires fail-closed refusal until packaged. These records are constraints, not implementation proof.

**Minimal next slice:** resolve the helper build/package mechanism choice; create the separate XPC helper and its minimal signed service product; integrate helper build/embed/independent signing before app signing in the Tauri macOS package flow; add the RPC-backed macOS `process_sandbox::spawn` implementation preserving child I/O/wait/cancellation; make the macOS CI matrix build the helper before the existing TG4-18 corpus; then add the TG4-31 stage/copy-back and security negative/positive tests. Until that last evidence exists, retain fail-closed refusal and leave P4-11/P4-61/TG4-18/TG4-31 open.
