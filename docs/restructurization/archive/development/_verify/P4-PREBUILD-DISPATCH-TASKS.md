### A. Worker status tasks and current schema — confirmed gap, but P4-01/02 wording is incomplete

- **P4-01 — PARTIALLY CONFIRMED.** `arcana-core/src/db/workers.rs:55-93` defines `WorkerStatus` and exhaustive `as_str` matching, but the persisted `Worker.status` field remains `String` (`:108-115`) and `WorkerStatus::from_str` silently maps every unknown string to `Created` (`:81-91`). The enum does not type the DB row or prevent invalid reads/writes. Recommendation: retain the enum objective but define its production read/write seam and prove a DB row with an unknown value fails at that seam; otherwise an enum-only test is circular.
- **P4-02 — CONFIRMED, with a contract mismatch.** `WorkerStatus::from_str` defaults unknown values to `Created` (`arcana-core/src/db/workers.rs:81-91`). The task text says loud error, but specifies `FromStr`; no `impl std::str::FromStr` was found by the repository search. Current `Worker` stores a `String` (`:108-115`), so callers can avoid parsing entirely. The gate TG4-01 does specify unknown DB reads fail (`TESTING_GATES.md:395`), making the intended contract clearer than the task. Recommendation: name the DB row hydration/read API and its test, not just a parser trait.
- **P4-03 — CONFIRMED.** The current `workers` DDL declares `status TEXT NOT NULL DEFAULT 'created'` with no `CHECK` (`arcana-core/src/db/workers.rs:182-201`). The `open_at` migration ladder is already in production (`:161-210`); adding a constraint to existing SQLite tables is a schema migration/rebuild decision, not a fresh-schema-only edit. The task's `LIVE-DB-PROVEN` label is risky under §0.8 because test coverage cannot write the user's `~/.arcana/workers.db`; settle with an isolated copied/synthetic legacy DB migration test and explicit backup requirement for any real DB operation.
- **P4-04 — PARTIALLY CONFIRMED; interval requirement is absent from the task.** `arcana-core/src/recipes/scheduler.rs:166-209` still runs cron schedules, with a 10-second minimum wait (`:176-182`); startup also runs an immediate tick (`:115-155`). I found event/kick call paths elsewhere, but this source does not show cron being demoted to a low-frequency reconciler or state a reconciliation interval. TG4-04 is epic assignment, so it does not support this task. The existing wording says “with a stated interval” but names neither the interval nor the event source/fallback semantics; specify those from the vision anchor before implementation, or mark the interval an owner decision.
- **P4-31 — CURRENT MECHANISM CLAIM OVERSTATED / historical defect resolved.** The current `Recipe` has no `fallback_policy` field (`arcana-core/src/recipes/types.rs:50-91`); its legacy YAML test verifies that field is ignored and not serialized (`:168-245`). The current ci gate is explicitly “mode2 and fallback policy are gone” (`src-tauri/src/ci_gate.rs:2825-2870`), while P4-31's checked completion narrative still says all eight recipes “now declare `Mode1Capable`” and describes `orch_healthy` pinned false (`MASTER_DEVELOPMENT_PLAN.md:1427`; current runner deletion recorded at `:1720-1723`). The underlying no-fallback runtime outcome is addressed, but the completed task's active-sounding proof text is stale after P8. ### B. P4-05…P4-10 — dispatch, ownership, and transaction claims

- **P4-05 — CONFIRMED.** `RecipeScheduler` maps any `WorkersDb::open/get_by_slug` error to `None` (`arcana-core/src/recipes/scheduler.rs:212-216`); the `None` arm logs paused/deleted and `break`s the schedule loop (`:288-293`). A transient SQLite read error therefore terminates the worker schedule, exactly the stated defect. Existing source has no retry around that read. TG4-02 must inject the error at this path and assert the same worker remains scheduled and resumes; a generic DB retry test would not prove it.
- **P4-06 — PARTIALLY CONFIRMED, with one stale/missing half.** `kick_worker` has an RAII guard for synchronous returns before spawn (`scheduler.rs:402-420`) but after spawn the async task clears `kick_inflight` only on its final normal path (`:493-510`); panic/cancellation skips it, which P4-37 correctly isolates. I found no timeout around `runner.run_recipe` in the kick task (`:498`), and no timeout symbol in `runner.rs`; so the timeout half remains open. Recommendation: distinguish synchronous-return cleanup from spawned-future cancellation/panic safety, and specify what timeout cancellation means for the in-process runner/task claim.
- **P4-07 — CONFIRMED.** `claim_task_with_pid` performs a separate worker-load read (`tasks.rs:1112-1128`) then `UPDATE ... WHERE id=? AND status='assigned'` only (`:1133-1140`), overwriting `assigned_worker` with the caller argument without asserting the previous owner. `ClaimTaskTool` first reads the task, then prefers its existing DB owner over caller identity (`claim_task_tool.rs:55-105`), so the tool does not reject worker B trying to claim A's task. The distinct `claim_next_ready` is one `UPDATE` with the load predicate inside it (`tasks.rs:1181-1202`), but whole-repo call-site search shows it is used by `src-cli/src/commands/task.rs:218` and tests only. TG4-03/S4-05 must drive the fleet's actual `claim_task`/recipe caller with two identities; a `claim_next_ready` concurrency test is the wrong path.
- **P4-08 — CONFIRMED.** The one-task guard is the pre-flight `SELECT COUNT(*)`, outside the write (`tasks.rs:1112-1128`); DB errors are swallowed by `.unwrap_or(0)` (`:1115-1120`) and then the claim proceeds. Concurrent claims by the same worker can both observe zero. `claim_next_ready` has a better atomic subquery (`:1191-1198`), but its CLI-only consumer does not satisfy the recipe path. Test the production call and inject both concurrency and read failure.
- **P4-09 — CONFIRMED.** `create_epic` inserts an epic with `status='ready'` and no worker (`tasks.rs:1521-1534`). Both single and batch assignment validate only the state/worker roster and do not inspect `task_type` (`assign_task.rs:84-109`; `assign_tasks_batch.rs:138-188`); `claim_task_with_pid` similarly filters only task ID/status (`tasks.rs:1133-1140`). `claim_next_ready` also has no task-type predicate (`:1191-1198`). TG4-04 is justified and must cover both assign and claim paths; a test of just the high-level assign tool may miss the DB claim seam.
- **P4-10 — PARTIALLY CONFIRMED / scope too broad to close as written.** Task DB contains status transition guards in a migration (`tasks.rs:452-514`) and a transaction for `clear_all` (`:803-834`), but no `transaction()` appears in `unblock_ready_tasks` or batch assignment. `unblock_ready_tasks` loops over per-dependent updates, emits events, then separately completes the epic (`:1697-1767`); `assign_tasks` writes each entry independently (`assign_tasks_batch.rs:105-219`). TG4-22's crash criterion (“no half-assigned task, no orphaned claim, no epic with a phantom child”; `TESTING_GATES.md:459-460`) does not identify which of these operations must be all-or-nothing or whether a partial batch is an allowed result. Recommendation: enumerate operations and expected commit boundaries before adding transactions; do not infer that every multi-row batch must roll back as one unit.

- **P4-39 — PARTIALLY CONFIRMED; contains an owner-policy question.** Budget exhaustion writes `needs_info` (`arcana-core/src/db/tasks.rs:1423-1428`); phased tasks with blockers also start there (`:1545-1569`); the transition trigger permits `needs_info → ready|failed|cancelled` (`:501-502`), so it is not intrinsically terminal. - **P4-40 — PARTIALLY CONFIRMED; stale-claim consequence is real on reassignment.** In `update_status_with_reason`, the branch with `Some(worker)` changes status/owner/reason but leaves `claimed_by_pid` and `claim_host` untouched (`tasks.rs:733-740`); only the `None` branch clears them (`:759-765`). `get_orphan_candidates` includes both `assigned` and `in_progress` (`:1232-1249`), and the reconciler uses the retained PID/host before the four-hour fallback (`orphan/mod.rs:147-176`). The broader phrase “every non-claim status write” has many direct SQL writers, so define whether the invariant belongs in a DB trigger/shared transition API; do not assume fixing this one helper covers lifecycle, budget, epic, and recovery writes.
