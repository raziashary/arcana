## Finding — partial daily cost backfills overwrite earlier expired batches

**Confirmed data-loss defect:** `AnalyticsDb::prune_append_only_before` aggregates only the token rows that are still present and older than the current cutoff, then writes each date with `INSERT OR REPLACE INTO daily_costs` (`arcana-core/src/analytics/db.rs:867-961`, especially `:952-961`). The scheduled lifecycle advances the timestamp cutoff continuously from `Utc::now() - 90 days` (`analytics/aggregator.rs:40-45`), so rows from one historical local date can expire across multiple hourly runs. The first run stores that first batch's daily totals; later runs aggregate only newly expired remaining rows and replace the same date, discarding earlier batches. The required preservation of cost history is therefore not proven and the current implementation can lose it.

The current test `raw_analytics_retention_prunes_strictly_before_cutoff_and_keeps_daily_history` exercises one expired token row for one date, then repeats the same cutoff after the row is gone (`analytics/db.rs:1777-1834`); it cannot expose advancing-cutoff partial batches. The production scheduled test also has one expired token row (`:2526+`).

**Focused proof/fix evidence needed:** seed multiple token rows on one local date on both sides of two sequential cutoffs; prune at cutoff A then cutoff B; through `get_daily_costs_range` and production CLI export, assert final daily totals equal the sum of every deleted row across both runs, and rerunning the same cutoff is idempotent. Preserve any pre-existing same-date summary without double-counting. Include provider and agent breakdowns, sessions, messages, tool calls and token totals; add the focused regression on Windows/Linux. Resolve the writer by accumulating prior backfilled summary or by a durable per-row/aggregate strategy that makes repeated pruning idempotent.

## Remaining findings and close evidence

1. **Confirmed cost-history data loss across a partial retention day.** A normal daily summary is already created from the complete local civil day (`aggregator.rs:57-98`; `get_token_usage_by_date` uses `local_date_range_bounds` at `db.rs:461-479`). The retention cutoff is an advancing UTC instant (`aggregator.rs:40`), while backfill groups only rows expired by that instant using SQLite local date (`db.rs:11-13, 856-961`). It then replaces `daily_costs` for that date (`:952-961`). Thus the first partial batch can replace a complete pre-existing daily summary while later same-date raw rows remain unexpired; subsequent hourly batches replace the preceding batch's summary again. This loses cost/token/session/message/tool totals and provider/agent breakdowns. The existing retention regression inserts one expired token row, one cutoff row and one newer row, and seeds its old cost summary on an unrelated date (`db.rs:1777-1834`), so it cannot prove same-date overlap or advancing-cutoff accumulation.
   - Required evidence: a date whose full daily summary already exists, with token rows inside and outside two successively advancing UTC cutoffs; after both prunes, query `get_daily_costs_range` and run the real CLI export. Assert full-day totals and all provider/agent buckets are preserved exactly once, remaining raw rows are not double-counted, repeat at the same cutoff is idempotent, and the local civil-date mapping matches normal daily aggregation. Run focused behavior on Windows and Linux. Owner disposition is needed before changing the persistence contract.

2. **TG4-21 migration-preservation clause remains unproven.** The analytics ladder's v1-v5 changes are additive, including monthly-table creation, but no test opens a populated pre-retention analytics DB through the production ladder and asserts historical rows and aggregates survive. `existing_analytics_default_is_normalized_by_startup_trigger` starts with an empty legacy `api_failures` table, migrates, then checks only a new default timestamp (`analytics/db.rs:2828-2879`). The shared CLI legacy-schema test constructs an in-memory older reader schema (`src-shared/src/db/analytics.rs:391-397`), not an upgrade/preservation path. Gate evidence says deployed migration preservation is “not needed” because deletion is additive-free, while the same note leaves existing-data compatibility open (`TESTING_GATES.md:1094`). TG4-21 explicitly names migration preservation at `:466`.
   - Required evidence: either a production-opener upgrade fixture seeded with old rows across token/event/failure/daily-cost/worker tables plus pre-existing hook logs, asserting all non-expired data and existing aggregate history survive the applicable analytics/config migrations; or owner-approved, gate-recorded rationale that migration preservation is inapplicable because the retention change adds no migration and existing upgrade guarantees are covered elsewhere.

3. **The documented CLI lifecycle wiring does not match current host calls.** MDP P4-59 says the shared hourly pruning job is used by desktop and CLI (around line 1537), but the only production CLI runtime call found is Fleet and it explicitly sets `start_analytics_rollup: false` (`src-cli/src/commands/fleet.rs:73-81`). The CLI `analytics export` path is a retained-history reader; its subprocess test invokes export after manually calling the pruners (`src-cli/tests/analytics_export.rs:108-121`). The desktop runtime uses default options and starts the job (`src-tauri/src/main.rs:72`; `arcana-core/src/runtime.rs:61-68, 145-146`).
   - Required evidence/decision: either wire an explicitly owned CLI maintenance lifecycle and prove it against an isolated profile, or amend the MDP claim and state that scheduled cleanup is desktop-owned while CLI provides read/export only. Do not start background cleanup implicitly in a bounded Fleet command without an explicit lifecycle contract.

4. **Three-host retention proof remains open.** Recorded active-writer proof passes the exact AnalyticsDb/HooksDb contention filter 2/2 on Windows and 2/2 on Linux, but macOS execution is pending/blocked by core-test compilation (`TESTING_GATES.md:1111-1115`, MDP checkpoint around `:2505`, current session checkpoint section “Three-host CI results and prerequisite repairs”). The subsequent prerequisite repair is not itself a macOS retention run. No three-platform result is claimed.
   - Required evidence: successful macOS execution of the exact active-writer filter, plus target-platform retention/export proof sufficient for any platform-specific timezone, SQLite locking or host-lifecycle behavior claimed by P4-59. Then reconcile the matrix and keep the gate open until all TG4-21 clauses are met.
