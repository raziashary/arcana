Pre-P8 Review

Your seven notes, investigated. Four background audits and a direct read of the prompt path. One data-destroying bug is fixed and pushed; ten decisions are yours.

Where to start

Two things changed my picture of the codebase, and both came from your notes rather than from the plan.

Note 1 has the opposite answer to the one you feared. Workers are strongly differentiated — the recipe carries a full role-specific prompt. But because the recipe replaces the base prompt rather than extending it, nothing that should be universal is: not the git rules, not AUTODEV.md, not the prohibitions.

Note 3 has a mechanism. Affinity is never consulted by any assignment. assign_task takes the worker slug from the model's tool arguments and only ever writes history. The scorer exists, learns nothing, and if called returns supervisor — which assign_task then rejects as invalid.

Decisions I need from you

Ordered so earlier answers unblock later ones — except D10, which sits last only because I found it last. It is the one with the largest effect on whether the fleet works at all. Each carries my recommendation; none of them are mine to make.

D1

Prompt architecture — should anything be universal?

A recipe's instructions replaces the base prompt entirely. So the seven prohibitions and the user's AUTODEV.md reach the interactive assistant and none of the agents that do the work.

I recommend: split the base prompt into a small invariant core — identity, the prohibitions, AUTODEV.md — that every agent gets, with the recipe adding to it. Recipes stay fully specialised; the safety floor stops being optional. The alternative is nine copies to keep in step, which is the shape that produced this.

D2

How should workers use git?

All five worker recipes run git add -A && git commit with no branch created first. On a fresh clone that is main. Nothing pushes, which is the only reason it is contained.

I recommend: create a branch before the first commit, and stage explicitly rather than -A. It is one line in five files. I have not touched it because how your fleet commits is a policy call, not a bug fix.

D3

Who executes the design work?

Your Note 4 is exactly right, and it is not ambiguity: across all of PD1–PD6 the words PA, fleet, worker and supervisor appear zero times. PD4-02 does say "no model call inside the tool", so adaptation is deterministic — but something still has to choose target sizes, handle a degraded result, and apply a brand guide, which is judgement.

I recommend: Rollout 1 answers the contract with deterministic tools plus the PA for the judgement cases; the fleet becomes an additional consumer in Rollout 2. Either way PD0 needs a task that states the execution model, so AutoDesign is not left to infer it.

D4

Fleet before design, or after?

P4 is currently sequenced after PD6. So through all of Rollout 1 — including handover — there is no working fleet. If D3's answer is "the fleet executes", this dependency is backwards.

I recommend: leave the order if D3 is "tools + PA". Move P4 earlier only if you want the fleet driving design work in R1.

D5

Where does procedural memory at tool execution live?

Your Note 2. tool_executor.rs does not consult memory at all today, so this is a new capability rather than a repair. P3-F is closed and appending to a closed phase is what the plan's own rules forbid.

I recommend: P4, since a worker repeating a build it has run before is the beneficiary. Bounded as: retrieved once per turn not per call, run through the flattener P3-F added, and advisory context only — never an input to a tool's arguments.

D6

ROI scoring — define it or drop it

You asked for ROI in the fleet. It does not exist in any layer: no model, no writer, no reader, no UI, and no task. The only "ROI" in the tree is QC cost per task. This is net-new, not a repair.

I need from you: what the score is over — business value, effort, cost, or a ratio — who writes it, and whether it orders dispatch ahead of the existing p0…p3 priority. I can't write the task without that.

D7

How much design UI does Rollout 2 need?

Your Note 7 instinct matches the plan — P6-25 and P6-28 already put design surfaces in AutoDev's own UI, correctly in Rollout 2. But two checkboxes for a Photoshop-like canvas is not credible: that is a layer tree, selection, transform handles, snapping, undo/redo and a properties panel.

I recommend: decide first whether R2 needs an editable canvas or only view + adapt + export. Editing is where nearly all the cost is, and AutoDesign already does it. Then scope it properly — 15–20 tasks, or its own phase.

D8

What happens to airsctl agent?

Five CLI subcommands — run, list, status, stop, logs — are pure HTTP calls to the Python orchestrator. After P8 they cannot succeed on any machine. This is the largest behavioural item in the sweep.

I recommend: reimplement run natively on the Rust engine and remove the other four. But removing a shipped CLI surface is your call.

D10

How should bash run a command on Windows? — highest impact of the ten

The rewriter translates POSIX pipes into PowerShell cmdlets and then executes them in cmd, which is why builds are recorded as failures. Fixing it is not a one-liner because there are three real options, and they differ in what you promise the model.

I recommend: stop rewriting, and run through a real POSIX shell where one exists — platform/command.rs was built in P1 for exactly this and still has no callers, which is what P4-11 is for. Falling back to PowerShell properly (not cmd) when none is present. The alternative is to keep the rewriter and fix it, which means owning a shell translator for ever.

D9

Restore the Live Monitor, or formalise that it is dead?

Worker tick telemetry — tick duration, last outcome, tick-start events — is emitted only from inside the dead Mode 2 branch. The UI that reads it is already permanently blank. Deleting that branch in P8 makes the breakage structural rather than accidental.

I recommend: re-emit it around the native engine run. It is a small addition and the fleet is hard to operate blind. The alternative is deleting the UI that reads it.

Defects found

Everything below I read in the code myself. Where a finding came from one of the four audits, I re-verified it before putting it here — several of their other claims I corrected or dropped.

Fixed & pushed edit_file destroyed files on an empty old_string

With replace_all, content.replace("", new) inserts the replacement at every character boundary — a 10 KB source file written back as thousands of interleaved copies, reported as success. Without it, find("") returns Some(0) for ever and the loop never advances: an infinite loop holding that file's lock so no other tool can touch it.

The schema marked old_string required but never non-empty, and a model meaning "insert at the top of the file" reaches for "" as the obvious way to say it. Refused now, with three tests that read the file back, and falsified by removing the guard.

Live Any recipe saved in the UI is silently stranded

FallbackPolicy defaults to Mode2Only, the field is #[serde(default)], and the recipe editor's payload omits it entirely. So a recipe you create in the UI deserialises as Mode2Only, hits the guard, and reports fallback_idle — it never runs, and never errors.

Worse: update_recipe does a full overwrite. Editing a shipped recipe through the editor strands it too — which silently undoes the P4-31 fix that flipped those eight recipes to Mode1Capable.

Live Affinity is never consulted by any assignment

assign_task and assign_tasks_batch take the worker slug from the model's arguments and call record_assignment only — they write history and never read it. The decision is made by the supervisor LLM from a keyword table in its prompt, which explicitly tells it to skip the scorer.

And the scorer cannot answer usefully anyway: its static layer requires confidence > 0.85 while the highest any pattern declares is exactly 0.85, so that branch is unreachable by construction. Outcomes are only ever written from a human clicking in the UI, so the learning gate never opens, every worker ties at 0.5, and the stable sort returns supervisor — which assign_task rejects as not a valid worker.

Live bash.rs rewrites POSIX pipes into PowerShell, then runs them in cmd

This is the one you said keeps failing, and it is BUG-COMPILE — the first bug in the whole restructure tracker — unrepaired. rewrite_for_windows emits Select-Object -First, Select-Object -Last and Select-String, which are PowerShell cmdlets. Line 116 then hands the result to cmd /C, which has none of them.

So npm run build 2>&1 | tail -50 becomes a pipeline whose right half does not exist. cmd reports the last element's status, the build evidence records a successful build as failed, and update_task_status reads that to veto qc_review. The work is done and the board says it failed.

Two more in the same file: nothing ever kills the child — no kill_on_drop, no process-group kill — while validate.rs and e2e_probe.rs both set it, so a timed-out cargo build holds target/.cargo-lock and every later build in the session times out too. And the rewrites are ordered so the grep -i branch can never match.

Live The build-evidence gate matches command text

bash("grep -rn \"npm run build\" package.json") exits 0, is classified as a passing Node build, and opens the qc_review door with nothing built. The gate that decides whether work may be marked complete can be satisfied by a command that mentions a build.

Live The UI overstates how long work has waited

A plausible amplifier of your original complaint. The QC queue parses an offset-less timestamp with an RFC3339 parser and falls back to zero, so every review reports an age of 0s and the stalled-review alert can never fire. The frontend has the same bug in the other direction — new Date("2026-09-01 06:23:58") is read as local time, so at UTC+5:30 every age is inflated by five and a half hours. A task assigned a minute ago can read as "6 hours ago".

Note 1 · shared base prompt

Workers are differentiated. What is missing is the shared floor, not the specialisation.

Each recipe carries a substantial role-specific prompt — 5,443 to 12,483 characters, with genuinely distinct protocols. worker-cleanup has a five-criterion "Demonstrably Unused Standard" and a mandatory functionality check that the base prompt has no equivalent of. A backend worker and a frontend worker do not behave the same.

The problem is the mechanism: the recipe is passed as system_prompt_override, and the engine treats an override as a total replacement.

Note 1-extra · legacy sweep for P8

37 proposed tasks, and one ordering constraint that would break the build if missed.

The sweep separates two things that share the words "Mode 1 / Mode 2" and must not be conflated. PAMode is fully live — it selects the prompt and the tool registry on the interactive path, and should not be swept up. FallbackPolicy is the inert half, and it is the live landmine in the defects above.

P8 must re-point a gate before it deletes anything

TG-P4-31 reads the literal let orch_healthy = false out of the runner and panics if it is gone. That is deliberate — it forces Mode 2's revival to be a visible decision — but it means the gate has to be rewritten first, or the first deletion commit fails CI for a reason that looks unrelated.

Beyond the sidecar itself, the sweep found ~106 lines of shipped in-app documentation describing the Python architecture, a base prompt that contradicts itself on lock files and describes GitHub-Issues coordination that no longer exists, and a dashboard component reporting fabricated 99.8% uptime for a service being deleted. Full task list is in the repo.

Note 2 · procedural memory at tool execution

New capability, not a repair — and your poisoning concern is the right frame.

Three risks, all of which have already bitten this codebase: volume, since the fleet makes many calls per tick; injection, since P3-F just closed a hole where recalled memory could author the system prompt; and determinism, since tool behaviour that varies with what the agent remembers breaks replay evidence. See D5 for the shape I would propose.

Note 3 · the fleet

You were right that the algorithm exists. The deeper problem is that nothing calls it.

Fixing the scorer alone would change nothing, because no assignment path consults it. Beyond that, the audit found four distinct ways a worker goes permanently quiet while the roster still shows it scheduled: two statuses the cron gate does not match, a transient database error collapsing into the "deleted" branch, a worker stuck in working with no watchdog or heartbeat, and a dispatch slot that leaks on a panic.

On the features you named: epics are complete and unreachable — model, tools, commands and a UI tab all exist, and no recipe ever creates one, so the panel is permanently empty. Worker chat works agent-to-agent only when the recipient is already busy, because an idle worker's tick is short-circuited before it reads its inbox; there is no human-to-worker channel.
