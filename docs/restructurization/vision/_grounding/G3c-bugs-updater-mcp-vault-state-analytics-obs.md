# G3c — Bug Audit: updater / mcp_server / vault / state / analytics / observability

**Scope:** `src-tauri/src/updater/`, `src-tauri/src/mcp_server/`, `src-tauri/src/vault/`, `src-tauri/src/state/`, `src-tauri/src/analytics/`, `src-tauri/src/observability/`
**Method:** read-only line-by-line audit; every claim carries `path:line`
**Date:** 2026-08-31
**Status:** COMPLETE

> **Headline — the two most severe findings in the entire audit live here:**
> 1. **The auto-updater performs no cryptographic verification when a release ships without sidecar files** (IN-01/02/03/04/05). It is a remote-code-execution path.
> 2. **The in-process MCP server exposes `bash`, `write_file`, `edit_file`, and `spawn_subagent` on localhost with no auth, no Origin validation, and a caller-chosen working directory** (IN-06/07).
>
> All paths below are relative to `src-tauri/src/` unless stated.

## PART 2: MODULE NARRATIVES

### mcp_server

Exposes AutoDev's canonical Rust `Tool` implementations over MCP Streamable HTTP so fleet workers can call them. Mechanically it works: spawned from Tauri's setup hook (`main.rs:241`), binds `127.0.0.1:8767` with `SO_REUSEADDR` before bind (`server.rs:78`), three-port fallback (`:35`), axum router at `/mcp`. **It is localhost-only — not `0.0.0.0`** — so the network-exposure concern is answered in the negative.

**The headline defect is the security posture.** `server.rs:199` states plainly "No auth middleware — localhost-only, in-process, zero external exposure," and the registry it serves includes `BashTool`, `WriteFileTool`, `EditFileTool`, and `SpawnSubagentTool`. There is no `Origin` validation, no session token, no bearer check. **"Localhost-only" is not an access control on a desktop machine**: every other process running as the user can reach it, and a browser page can be made to POST to it. `tool_adapter.rs:181` compounds this by letting the caller specify `__working_dir` for every call, so the requester also picks the jail root.

`health_monitor.rs` is the least reliable file: its 5-second timeout is defeated by `.unwrap_or_default()` (IN-38), its state machine has a dead end that permanently strands a server that was down at startup (IN-39), stdio transports are reported healthy by assumption (IN-43), and nothing registers the in-process server itself (IN-45). On the positive side, **every event this module emits has a real frontend listener** in `src/stores/sidecarStore.ts:203-309`. No orphan events.

### vault

**To answer directly: yes, it encrypts, in the sense that matters.** The 66 lines are a thin, correct wrapper over the `keyring` crate (Cargo.toml:44), delegating to Windows Credential Manager, macOS Keychain Services, and libsecret/KWallet. No plaintext file, no home-rolled crypto, no key management to get wrong, no hardcoded secret. `get` correctly distinguishes `NoEntry` from a real failure. **For a 58-line file this is the right design.**

**The problem is not the vault, it is the door next to it.** `commands/vault_commands.rs:12` and `:27` expose `get_provider_key` and `get_github_pat` as Tauri commands returning the raw secret to the webview (IN-47). Anything executing in the frontend can `invoke('get_github_pat')` and read the token, and the CSP permits `connect-src https://api.github.com`, so **exfiltration to a plausible-looking destination is allowed by policy**. Nothing in this module logs a secret, which is good, but pulling secrets across the IPC boundary at all is the wrong shape; the keychain should be read Rust-side at the point of use.

### state

67 lines of lightweight runtime flags behind `Arc<Mutex<>>`. Structurally fine. The functional defect is semantic: `cost_today_usd` and friends are named "today" but are only ever incremented, with no midnight rollover and no reset anywhere. `queries.rs:55` then uses `live_cost_usd` verbatim as the dashboard's headline `today_cost`. **So the most prominent number in the app means "since process start"** and drifts wrong in both directions across a midnight boundary or an app restart (IN-50).

### analytics

The pipeline is Events → Collector → SQLite → Aggregator → Dashboard. `token_usage`, `worker_stats`, `system_events` and `daily_costs` are all genuinely read. **But the inverse defect exists and is critical:** `record_api_failure` has **zero** callers anywhere outside the analytics module, while `get_api_failures` is read by the UI. The API-failures panel is permanently, structurally empty (IN-53). A second mismatch: the startup diagnostic queries `hourly_costs`, a table `migrate()` never creates (IN-54).

The SQL layer has systemic problems. Every hot query wraps the indexed timestamp in `DATE(timestamp)`, making the index unusable and turning each dashboard load into a stack of full table scans (IN-63) against tables with no retention policy at all (IN-64). Two queries compare RFC3339 text against `datetime('now', …)` output; because `T` sorts above a space, **the "last hour" filters are decorative** (IN-59/IN-60). And there is a pervasive local-vs-UTC split, so **every daily figure is wrong by the user's offset** (IN-61/IN-62).

The rollup barely runs: it sleeps a full hour before its first execution and only ever aggregates *yesterday*; a desktop app used in sub-hour sessions never completes a single rollup (IN-56). `run_hourly_rollup` is a bare `Ok(())` stub whose doc promises aggregation (IN-55). Error handling leans on `.unwrap_or(0)` throughout, making a broken schema look exactly like an idle day (IN-66/IN-73) — a regression against the very failure mode `queries.rs:77-80` says it was fixing.

### observability

**To answer the deletion question precisely:** `stray_files.rs` **does not delete anything** — it only walks, warns, and emits `workspace:strays-detected` (which does have a listener, `WorkspaceMismatchBanner.tsx:127`). `log_retention.rs` **does** delete via `remove_file` at `:72`, but the blast radius is well contained: non-recursive, gated on an `autodev-` prefix, further gated on mtime. A wrong or empty root causes a no-op, not data loss.

The stray scanner is the broken one: misrooted at `current_dir()` so it almost never examines the pair it documents (IN-78), and its "am I inside src-tauri" test is a substring match against the full absolute path, so a checkout under any ancestor containing that string **flags the entire React frontend as strays and offers to delete it** (IN-79).

### updater

**The most dangerous module in the audit.** To answer the signature question: **verification is real code but it is not a gate — it can be bypassed by simply not providing a signature.** The exact line is `verify.rs:90`: `if !sig_url.is_empty() {`. When the sig URL is empty, the entire Ed25519 branch is skipped and `verify_update` returns `Ok(())`. `verify.rs:18-21` does the same for checksums. And `check.rs:136-137` sets both fields to `String::new()` whenever a release lacks sidecar assets. **Chain them and a release published without sidecars is installed with zero cryptographic verification, in release builds, on every platform.** `updater_commands.rs:111` widens the hole further, converting a transient network failure into an empty string. **This is an unverified auto-updater and therefore a remote-code-execution path.**

Even the "working" branch cannot work. `EMBEDDED_PUBLIC_KEY` is base64 for the ASCII string `undefined-public-key-for-development-only-placeholder` — 53 bytes, not 32. So there is **no configuration in which a genuine signature verifies successfully**: shipped builds either skip verification (no sig) or reject every signature (sig present, placeholder key).

On the "you cannot replace a running .exe on Windows" question: the code sidesteps it via `RunOnce`. That does avoid replacing the running binary — but `RunOnce` fires at the next **logon**, not at app restart, while the returned message says "Restart AutoDev to apply" and the command immediately calls `app_handle.restart()` (IN-14). macOS writes a LaunchAgent that is never loaded and never cleaned up (IN-15). **Linux is worse: `schedule_linux` writes a script and returns `success: true`; nothing anywhere ever executes it** (IN-13).

The delta-patch path is non-functional in every direction (IN-08 through IN-12, IN-93).

**Two cross-cutting answers:** nothing in this scope shells out to a compiler or build tool. The complete set of process spawns is `netstat`/`lsof`/`ss` in `port_status.rs` and `reg.exe` in `install.rs:101`, plus generated-but-never-executed shell scripts. **Redis is not a dependency of any module in this scope** — no `redis` crate in Cargo.toml; the only Redis contact in the whole crate is a raw-TCP PING in `sidecar/client.rs:558`.
