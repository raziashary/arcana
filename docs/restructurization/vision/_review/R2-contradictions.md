## 1. Executive summary — the contradictions that would cause wrong code

Eight findings, in the order I would resolve them.

**1. Two ADRs pick two different web-search providers, and one adopts a capability the other rejects.** ADR-01-05 was answered *"We do all 1 - 8 now"* — row 8 is *"Route hosted web search to **xAI** at $5/1k"*. OQ-4 was answered *"Google."* — the most expensive of the three the plan itself priced. Separately, ADR-01-05 rows 12–14 are **"SKIP hosted RAG"**, while ADR-02-08 adopts *"(B) web search + file search"* — provider file search **is** hosted RAG, and it uploads the user's files to a vendor in a product whose non-goals include *"Not shipping a hosted/multi-user AutoDev. Single user, single machine, local-first."* Whichever a builder picks, one answered decision is violated. → **X-01, X-02**

**2. `airsctl` is a second process running agents, and three other decisions assume there is only one process.** ADR-01-02 was answered *"the `airsctl` also become an in process agent house itself"*; ADR-01-03 adds *"the entire app can be run from the cli"*. Meanwhile S6 states *"After M-29 there is exactly one AutoDev process"*, INV-1 forbids agent work *"outside the AutoDev process"*, and ADR-04-04's decisive argument for deleting Redis is *"A warm tier exists to share state **between processes**. After P8 there is one process."* Spec `08 §3.2` has already noticed and quietly contradicted the plan: *"With `airsctl` in the picture (ADR-01-03) this is a live multi-process concern, not a theoretical one"*, and its gate **G-CONCURRENT** asserts *"Two processes writing the same database both succeed."* → **X-05, X-13, X-14**

**3. ADR-01-03's answer requires the MCP server that ADR-03-02 deletes.** *"the `sec-cli` is the one that makes the AutoDev can run as an MCP server"* versus *"We do option A for now, we delete it first now"* and P8's *"the now-dead deps (`ollama-rs`, `dotenvy`, `sysinfo`, possibly `rmcp`/`axum`)"*. `rmcp`'s server features are the only MCP-server capability in the tree. → **X-06**

**4. ADR-02-02's answer permits exactly what Part 2 forbids absolutely, and two other documents silently narrow it.** Razi: *"imagine A combined with B but A is the main path, and only do B after say three consecutive failures."* **Option (B) is "Keep model-authored but supply per-OS command templates."** Part 2.2's Forbidden table has no exception clause: *"Authoring the build/test command → replaced by DET ecosystem detection + Rust-controlled argv (M-13)"*. M-13 and spec `04 §4.1` then restate the answer as *"the model diagnoses, it never reports the verdict"* — a narrowing nobody decided. The failure this re-opens is SK-50 itself: a model authoring a build command on Windows. → **X-07**

**5. Two Group E memory ADRs disagree about whether autonomous memory creation is in scope.** ADR-05-04 adopts *"the anchor's §18 evaluation"* and introduces `propose_memory`; anchor §18 is titled **"Autonomous Memory Creation"** and §22 Phase 5 is *"Autonomous Memory — Allow the agent to automatically identify useful memories"* with exactly that pipeline. ADR-05-05 defers *"Phases 4–6 (consolidation, contradiction resolution, **autonomous memory creation**, knowledge graphs, multi-hop retrieval)"*. Spec `03` carries both, four paragraphs apart (§4.5 vs §4.6). → **X-03**

**6. ADR-05-05's load-bearing "the two agree" claim is false.** *"the anchor's §10 reranker **is** the competitive model, so the two decisions agree"*. They are different formulas: the anchor's §10 scores on `lexical_relevance + importance + access_frequency + scope_match + task_similarity + confidence`, none of which appear in the ported model (spec `03 §4.2`: `relevance, authority, recency, type_bonus, priority, correction, session_anchor, procedural_fit, length_penalty`). Because they are said to be the same thing, **no work item exists for the anchor's reranker**, and Phase 2 has nothing to ship. → **X-04**

**7. The anchor mandates Google-Fonts-loaded typefaces; the plan mandates self-hosting, and the same CSP that broke Graph City would break the anchor's fonts.** `ui-anchor.md §Typography`: *"Three faces, all SIL OFL, **loaded from Google Fonts**"*. M-24 and spec `07 §5`: *"**Self-host the font**"*, with gate G-CITY requiring the app render *"offline"*. Unacknowledged anywhere. → **X-25**

**8. P4's exit gate cannot be met with the infrastructure P4 has.** P4 exits on *"A task runs end to end on **all three OSes**"*, while spec `10 §6` schedules *"The frameworks and the end-to-end smoke follow in P9"* and there is *"no macOS job at all"* today, with R-4's mitigation claiming *"macOS enters CI in **P0**"* — a claim P0's own contents contradict. → **X-21, X-22**

**The shape of the failure.** Six of the eight are **answer-vs-doctrine**, not answer-vs-answer: an ADR was answered correctly in its own frame, and a Part 1/Part 2 rule written earlier was never re-read against it. The suite's own instrument for this — the `⚠ CORRECTED` / `~~struck~~` convention — is used well where a claim was found wrong, and not at all where an *answer* narrowed or overrode a rule.

## 3. Findings by category

### 3.1 ADR-vs-ADR contradictions

**X-01 · X-02 · X-03 · X-04 · X-05 · X-06 · X-09 · X-11 · X-13**, plus the already-documented ADR-02-06 × ADR-03-02 collision.

Two clusters account for all of them.

**Cluster A — the memory decisions (ADR-01-06/07/08 vs ADR-05-01…05-05).** ADR-01-06's answer (A+C) and ADR-01-08's answer (B-then-A) were given against the *sidecar port*; ADR-05-01…05-05 were answered days later against the *anchor*. They were never reconciled term by term, and three seams opened:
- **X-03** — ADR-05-04 adopts the anchor section (§18 "Autonomous Memory Creation") whose phase (§22 Phase 5) ADR-05-05 defers.
- **X-04** — ADR-05-05 declares the anchor's §10 reranker and the sidecar's competitive model to be the same thing so that ADR-01-08 and ADR-05-05 "agree". ### G-02 — Provider-hosted file search: adopt or reject
**The call:** ADR-02-08 adopts *"web search + file search"*. ADR-01-05 rows 12–14 are *"**SKIP** hosted RAG"*. Which stands?
**Why it matters:** Vendor "file search" is hosted RAG — a vendor-side vector store over uploaded content. Adopting it (a) contradicts an adopted row of ADR-01-05, (b) sends workspace content to a third party in a product whose non-goals include *"Single user, single machine, local-first"*, (c) duplicates `sqlite-vec` + FTS5, which ADR-05-01 chose specifically to keep retrieval local and offline, and (d) adds a second unprompted egress path beside the one spec `06 §1.1` already flags as its sharpest finding (*"`analyze_diff` … **uploads the full diff of any repository to a third-party LLM**"*, unprompted because it declares `is_read_only`). **Under BYOK it is the user's own key, the user's own code, and the user's own bill.**
**Options:** **(A)** Reduce ADR-02-08 to web search only. **(B)** Keep file search, and record an explicit exception to ADR-01-05 row 12 plus a `Network` permission prompt (per spec `06`'s `ToolEffect`) on every use. **(C)** Adopt none (ADR-02-08 option C).
**Recommendation:** **(A)**. Web search fills a real gap (*"the sidecar had Tavily; the Rust side has nothing"*). File search fills a gap the memory system already fills, locally, for free, offline. ### G-03 — Is the memory gateway in scope, or is it Phase 5?

### G-04 — Which reranker is Phase 2, and which columns does it need
**The call:** ADR-05-05 asserts *"the anchor's §10 reranker **is** the competitive model"*. It is not. Which formula ships in Phase 2 — the anchor's §10 score, or the sidecar's two-stage competitive utility from `G4c §4.4`?

### G-05 — What INV-1 means now that `airsctl` runs agents
**The call:** ADR-01-02 (A) puts an agent runtime in a second process. INV-1 says *"No agent work happens outside the AutoDev process"* and S6 says *"exactly one AutoDev process"*. Restate the invariant, or change the decision.
**Why it matters:** INV-1 is the premise of the whole programme, and as written it is now false by design. Its gate tests only for Python spawns, so it would pass while a second Rust agent process runs — a gate that cannot fail (INV-4). Three downstream designs assume single-process: ADR-04-04's Redis rationale, spec `08`'s connection strategy (which has already contradicted S6 in `G-CONCURRENT`), and the keychain-only credential model (G-08).
**Options:** **(A)** Restate INV-1 as *"No agent work happens outside an AutoDev-signed binary linking `autodev-core`. No interpreter, no daemon, no localhost agent API, no network hop."* Restate S6 as *"one long-lived desktop process; `airsctl` is a second, short-lived, non-daemon process sharing the same on-disk state under WAL."* **(B)** ADR-01-02 option (C) — demote `airsctl` to a board/config client; agent execution is desktop-only. **(C)** ADR-01-02 option (B) — `airsctl` drives the running app over local IPC (rejected once as "a local daemon by another name", but it *does* preserve INV-1 literally).
**Recommendation:** **(A)**. ### G-06 — "AutoDev as an MCP server", and who owns the tool-registration surface after the MCP server dies
**The call:** ADR-01-03's answer says `src-cli` is *"the one that makes the AutoDev can run as an MCP server"*. ADR-03-02 deletes the server and P8 drops `rmcp`. Is MCP-server exposure a product commitment? And — the larger half — **what replaces `register_for_mcp_worker` as the per-consumer tool matrix for workers, the Supervisor, and subagents?**
**Why it matters:** Two things die with `mcp_server/`, and only one is planned for. `G10 §1.1`: *"`register_for_mcp_worker` … **34**"* is the worker/Supervisor surface, and *"**Subagent has no registration path of its own** … a subagent surface **is** the worker 34."* Spec `01 §5` designs the subagent lifecycle and never says which tools a subagent gets; spec `06 §2` lists four registration entry points and does not say which survive. ### G-07 — The build-verification escalation contract
**The call:** ADR-02-02's answer permits option (B) — *"Keep **model-authored** but supply per-OS command templates"* — after three consecutive failures. Part 2.2 forbids model-authored build commands absolutely. M-13 and spec `04 §4.1` restate it as diagnosis-only. Which is the contract?
**Why it matters:** The literal reading re-introduces BUG-COMPILE on the retry path: a model emitting `2>&1 | tee build.log; echo "EXIT:$?"` into `cmd /C` is exactly SK-50, and it would fire precisely when a task is already struggling. `G-NO-POSIX` is a static check over prompts and recipes — it cannot catch a command a model composes at runtime.
**Options:** **(A)** Diagnosis-only: the model receives the failing argv, the exit code and the output, and returns a **structured** diagnosis (airlock law 2); Rust re-runs its own argv. The model never emits a command string. **(B)** Model-authored from per-OS templates, with the template set fixed in Rust and the model choosing among them by index — a bounded, typed choice rather than free text. **(C)** As answered: free-form model-authored commands after three failures.
**Recommendation:** **(A)**, with **(B)** as the extension if diagnosis alone proves insufficient. (B) is the honest reading of *"A combined with B"* that still satisfies Part 2.2, because the model selects rather than authors. **(C)** should be explicitly ruled out in the ADR text, since that is what the answer currently says.

### G-08 — The headless credential path
**The call:** `airsctl` is kept for *"headless CI/automation"* (ADR-01-02, OQ-1). INV-12 and ADR-03-05 permit exactly one runtime source — the OS keychain — and `G-KEY-NOENV` gates it. How does a headless runner authenticate?
**Why it matters:** No unlocked keychain exists in a headless session on any of the three platforms. With the `--api-key` flag removed (ADR-03-01) and no env fallback (INV-12), `airsctl` cannot make a model call in CI. Discovered mid-build, the fix under pressure will be the env fallback INV-12 exists to forbid — the exact "presence of a capability is not intent to use it" failure the plan names.
**Options:** **(A)** Drop the headless claim: `airsctl` is interactive-only, uses the same keychain as the desktop app, and OQ-1's "headless CI" justification is withdrawn. **(B)** An explicit, opt-in `--credential-file <path>` with a documented threat model, refused unless the file has restrictive permissions, and never consulted by the desktop binary. **(C)** A CI-only keychain service account (`gnome-keyring --daemon` / `security unlock-keychain` / Windows service account) — real, but per-platform CI work.
**Recommendation:** **(B)**. It is the only option that keeps the stated capability, and it satisfies INV-12's actual intent — the danger INV-12 names is a *silent* fallback that a runtime lookup satisfies by accident. An explicit flag that the desktop binary does not implement is the opposite of that. It must be paired with a static gate: *the desktop binary contains no credential reader other than the keychain*.

### G-09 — When the MCP HTTP server's exposure is closed
**The call:** ADR-03-02 was answered *"we delete it first now"*; Part 6 schedules the deletion in **P8**, after five other slices. Is the exposure closed earlier?
**Why it matters:** ADR-03-02's own description — *"no auth and no `Origin` validation … the registry it serves includes `BashTool`, `WriteFileTool`, `EditFileTool` and `SpawnSubagentTool`; the caller also supplies `__working_dir` … **Any local process, or a web page via DNS rebinding, gets arbitrary command execution**"* — is a P0-class finding sitting in the last-but-one slice. P0 is literally named *"Stop the bleeding"* and does not contain it. The deletion genuinely cannot move (it is coupled to `bridge.rs`'s SSE parsers, `00 §6`); the **exposure** can.

**Recommendation:** **(B)**, falling back to **(A)** if anything still depends on it during P2–P4. It is a config change, not a refactor, and it makes the coupling irrelevant. **(C)** is only defensible if the owner accepts a known local RCE for the duration of the restructure — which is a decision, not a default.

### G-10 — The context ladder on the three providers that lack Anthropic's context editing
**The call:** ADR-01-05 establishes `clear_tool_uses` as *"Anthropic only; no equivalent elsewhere"* and server-side compaction as absent on Google. Spec `03 §2`'s four-layer ladder is written provider-agnostically. What is layer 3 on OpenAI, Gemini and xAI?
**Why it matters:** The ladder is the direct answer to BUG-TOKENS. As specified it is complete only on Anthropic; on Gemini it is two layers, and nothing describes the gap between "live history" and "compaction". Two gates (`G-CLEAR-WORTH`, `G-COMPACT-FIRES`) cannot pass on all four providers as written.
**Options:** **(A)** A client-side equivalent: the context builder drops oldest tool results above a threshold and rebuilds the prefix boundary, applied on every provider; Anthropic additionally uses the server-side mechanism where it is cheaper. **(B)** Scope the layer to Anthropic; the other three rely on caching + compaction only, and the gates are scoped per provider with the shortfall stated. **(C)** Client-side only, everywhere — one code path, no server-side context editing at all.
**Recommendation:** **(C)** for the first build slice, **(A)** as the refinement. One client-side implementation is testable on all four, makes `G-CLEAR-WORTH` meaningful everywhere, and removes an Anthropic-shaped branch from the hottest path in the system. Adopt the server-side variant later only if measurement shows it wins.

### G-11 — What "memory first" means in ADR-01-06
**The call:** ADR-01-06 was answered *"combine both A and C, so **always memory first**"*. Option (A) is *"recall **replaces** history"*. The plan and spec `03` implement (C)'s ladder, in which recall sits inside the cached prefix and history is retained.
**Why it matters:** The two readings send materially different byte counts. If recall replaces history, `G-CTX-BOUND` becomes trivially satisfiable and `clear_tool_uses`/compaction become near-dead; if recall merely precedes history, the answer's (A) half is unimplemented.
**Options:** **(A)** Literal: above a turn threshold, recalled memory substitutes for older turns, which are dropped rather than summarised. **(B)** Positional (what is specified): recall is in the prefix, ahead of history; history is bounded by layers 3 and 4. **(C)** Hybrid: recall substitutes for turns it demonstrably covers, measured by the `G-MEM-VALUE` rediscovered-facts metric.
**Recommendation:** **(B)**, recorded explicitly as the reading of the answer — with a note that (A) was considered and is what layers 3/4 achieve by a safer route. Substituting recall for history risks dropping a turn the model needs and has no deterministic fallback (airlock law 3).

### G-15 — How the anchor's three typefaces are delivered
**The call:** `ui-anchor.md` — DOCTRINE — says *"Three faces, all SIL OFL, **loaded from Google Fonts**"*. M-24 and spec `07 §5` say self-host, and `G-CITY` requires offline rendering.
**Why it matters:** The CSP that makes troika's CDN font fetch hang forever — *"both `tauri.conf.json:28` and `index.html:8` block it in `connect-src` (`font-src` does not cover `fetch()`)"* — applies to the anchor's own faces. Either the CSP is opened to `fonts.googleapis.com`/`fonts.gstatic.com`, re-widening the egress surface INV-2 is narrowing, or the anchor's delivery mechanism is overridden. `G-ANCHOR` (*"fonts are the anchor's three"*) and `G-CITY` (*"renders … offline"*) cannot both pass on an offline machine today.
**Options:** **(A)** Self-host all three as bundled WOFF2 subsets; record the divergence from `ui-anchor §Typography` the way ADR-05-01 recorded the §21 divergence. **(B)** Keep Google Fonts and widen the CSP for the two font hosts. **(C)** Self-host, and additionally self-host the troika/drei font (which spec `07` already requires) from the same bundle.
**Recommendation:** **(C)**. All three faces are SIL OFL, so bundling is licensed. It is the only option consistent with an app whose memory system was deliberately made to work offline, and it removes a runtime network dependency from first paint. **The divergence must be written into the anchor register, not just done** — that is the discipline ADR-05-01 set.

### G-16 — The UI class vocabulary and the `.airs-*` naming lock
**The call:** `00 §5` locks *"`.airs-*` for the UI class vocabulary"* and four documents say the anchor has *"34 `.airs-*` classes"*. The anchor lists **38** classes of which **4** are `.airs-*`. Is the vocabulary re-prefixed, or is the lock restated?
**Why it matters:** `G-ANCHOR` and spec `10`'s anchor-conformance family would be written against a vocabulary that does not exist. Re-prefixing 34 classes is a change to a DOCTRINE document and needs the owner; leaving them is a change to a naming lock.
**Options:** **(A)** Restate the lock as *"the anchor's class vocabulary verbatim — 38 classes, of which `.airs-card`, `.airs-card-nested`, `.airs-badge`, `.airs-mono` carry the prefix"*; correct the count everywhere. **(B)** Re-prefix all 38 to `.airs-*` and amend `ui-anchor.md`. **(C)** Prefix only new classes; leave the anchor's as-is.
**Recommendation:** **(A)**. The anchor is doctrine and was written deliberately; the plan's job is to implement it, not to rename it. The "34" appears to have been derived by counting the *non*-prefixed subset, which is worth noting so the same error is not repeated in the gate.

### G-17 — Who produces `importance` and `confidence`
**The call:** ADR-05-04 makes the §18 evaluation *"`DET` policy, **not a model call**"*. Anchor §18 assigns *"What did I learn? … **How confident am I?**"* to the agent, and its examples carry model-produced scores (`"confidence": 0.97`).
**Why it matters:** Nothing in the plan defines how a deterministic gateway computes `importance` or `confidence` over free-form text. Built literally, they become a constant or a string-length heuristic — and the §10 reranker (G-04) then ranks on fields carrying no information, which would make the memory system measurably worse than lexical recall while appearing to work.
**Options:** **(A)** Split by kind: the **agent proposes** `importance` and `confidence` as typed fields on `propose_memory` (an ORGAN judgement returning structured output — airlock law 2); the **gateway deterministically** applies novelty, duplicate detection, scope validation and thresholds, and may clamp or reject. **(B)** Fully `DET`: derive importance from provenance class and confidence from source type (e.g. `user` = 1.0, `test_result` = 0.9, `agent_observation` = 0.6) — no model call, no free parameters. **(C)** As answered, with the definitions left to implementation.
**Recommendation:** **(A)**, with **(B)**'s provenance-derived values as the deterministic **floor** and fallback when the agent supplies nothing (airlock law 3). This is both anchor-faithful and Part-2-faithful: judging what was learned is an ORGAN act; deciding to persist is not — which is exactly what ADR-05-04 says, once the two halves are separated.

### G-18 — Which checkpoint system is truth
**The call:** `checkpoints` in `config.db` (`git/checkpoint.rs`, compiled, git-based) or `file_checkpoints` in `checkpoints.db` (`db/checkpoints.rs`, **not compiled**, file-based)? R3 and spec `08 §3.7` both say *"pick one"*; nothing picks.
**Why it matters:** P1 declares `db/checkpoints.rs` — putting the second system in the binary and creating the duplicate INV-10 forbids. M-38's undo affordance depends on the answer (*"`db/checkpoints.rs` is **not compiled**, so undo does not currently exist at all"*), and so does whether the destructive-action confirmations can offer undo or only confirmation.
**Options:** **(A)** Git-based wins; delete `db/checkpoints.rs` and `checkpoints.db` (P1 declares it only long enough for the reachability gate to be honest, then removes it). **(B)** File-based wins; `git/checkpoint.rs` becomes a caller. **(C)** Both, with a stated boundary: git checkpoints for committed state, file checkpoints for uncommitted single-file undo.
**Recommendation:** **(A)**. Git already provides the durable, inspectable, restorable substrate, and a second file-copy system is a second thing to get wrong. If per-file undo is wanted (M-38), it is better built on `git stash`-style objects than on a parallel database. Note this also removes one of the eleven databases (X-40).

### G-20 — `ToolEffect` as the permission key
**The call:** Spec `06 §1.2` replaces the permission model — *"`enum ToolEffect { Read, Write{paths}, Execute, Network{host}, Board }` … `ToolEffect` decides prompting"* — under M-09, whose owning ADR (02-03) is about subagents. No ADR decides this.
**Why it matters:** It is the plan's largest undecided design and it is a security model. The current state is that a **concurrency hint** gates auto-approval (`G10-111`), so two tools that act on the world are never prompted, including one that *"uploads the full diff of any repository to a third-party LLM"*. ADR-05-06 additionally makes the permission model the precondition for ever admitting third-party tools. A redesign this consequential recorded only in a spec is exactly what Part 8 exists to prevent.
**Options:** **(A)** Adopt `ToolEffect` as specified; `is_read_only` reverts to concurrency; `PermissionMode` is honoured; the gate runs once, on the single execution path (M-08). **(B)** Keep `requires_permission()` and simply start calling it — smaller, but it keeps a boolean where the finding is that a boolean cannot express network egress. **(C)** `ToolEffect` plus a per-effect default policy table that `PermissionMode` selects rows from.
**Recommendation:** **(A)**, escalating to **(C)** once the four modes are specified — the mode dropdown currently *"changes nothing"* (`agent_commands.rs:142` passes `ManualApproval` unconditionally), so what each mode means is itself undefined and should be written down with the effects. This needs a mechanic of its own; M-09 as written is one line about populating `ToolContext`.

### G-21 — Delta patching: delete or repair
**The call:** Spec `09 §3.3` recommends deleting the delta-update path. No ADR covers it.
**Why it matters:** Five independent defects, including *"`bzip2_decompress` is a passthrough stub"*, *"`new_size` is an unbounded attacker-controlled allocation"*, and *"`create_patch` emits `ctrl_len = 0`, so **nothing it produces can ever be applied**"*. ### G-22 — Integrity of the embedding-model download, and the fate of `dotenvy`
**The call:** Two loose ends from the ADR-05-02 retraction. **(a)** The ~130 MB BGE-small download is a runtime fetch of an artefact that is then executed by an ONNX runtime; INV-11's rule (*"absence of a signature is a failure, never a pass"*) is scoped to the updater and nothing equivalent covers this. **(b)** P8 and spec `09 §4` list **`dotenvy`** among *"the now-dead deps"* while ADR-03-05 requires a repo `.env` *"read only by the integration-test harness"*.
**Why it matters:** (a) is a second download-and-execute path in a plan whose first slice repairs the first one; the difference is that this one has no verification rule at all. (b) is a one-line dependency-section question that, answered wrongly, removes the reader for the `.env` the owner was told to create.
**Options:** **(a)** **(A)** Pin the model by SHA-256, verify before use, fail closed to lexical retrieval on mismatch. **(B)** Bundle the model in the installer (+130 MB, no download, no first-run step — which also removes the X-30 first-run problem). **(C)** As specified: download with progress, no integrity check. **(b)** **(A)** `dotenvy` moves to `[dev-dependencies]`. **(B)** The harness reads `.env` with a five-line hand parser and `dotenvy` is deleted outright.
**Recommendation:** **(a) (A)** — a pinned hash is trivial and makes the download auditable; **(B)** is worth costing, because trading 130 MB of installer for the removal of an entire first-run failure mode may well be the better product decision. **(b) (A)**, stated explicitly in P8's dependency list so the harness does not lose its reader.
