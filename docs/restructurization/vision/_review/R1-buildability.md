The defects are real and correctly located.

The failures below are almost entirely in the **forward** direction: mechanisms asserted to work that the platform does not provide the way the plan describes, properties asserted without an enforcing mechanism, and a build sequence whose gates cannot be met in the order given.

## 1 · Executive summary — the findings that change the plan

Ranked by how much of the plan they invalidate.

**1. The `sqlite-vec` stack composes — but the plan's retrieval design does not fit `vec0`'s filtering model (B-01, CRITICAL).**
The linking claim in ADR-05-01 survives scrutiny: `sqlite-vec 0.1.9`'s `build.rs` compiles **only** `sqlite-vec.c` with `-DSQLITE_CORE` and no SQLite amalgamation, so there is no duplicate-symbol fight with `rusqlite`'s bundled build. That specific suspicion is **disproven** and I say so plainly.
What does not survive is the row in ADR-05-01 and spec `03 §4.4` reading *"Metadata filtering → plain SQL columns"*. In a `vec0` KNN query only **metadata columns** and **partition-key columns** may appear in the `WHERE`; everything else is either an error or silently wrong, and auxiliary columns cannot filter at all. Scope (ADR-05-03) is declared a **mandatory retrieval filter** and gate `G-MEM-SCOPED` asserts it. As designed — scope as an ordinary SQL column joined after the KNN — scope becomes a *post*-filter over the top-k, so a selective scope returns few or zero results. The three memory decisions (05-01 substrate, 05-03 scopes, 05-05 hybrid retrieval) are individually reasonable and jointly unimplementable as written.

**2. `fastembed` drags in an entire undeclared dependency chain, and its default cache path violates the plan's own INV-5 (B-02, B-03, CRITICAL/HIGH).**
`fastembed 6.0.2` depends on `ort =2.0.0-rc.13` with default features `ort-download-binaries-native-tls` — a **build-time download of ONNX Runtime from a third-party CDN**, an exact-pinned release candidate, and a native-TLS/OpenSSL edge on Linux. None of this appears anywhere in the plan; ADR-05-02 discusses only a 130 MB model download. Separately, `fastembed`'s cache directory defaults to `.fastembed_cache` **relative to the process working directory** and is overridable by ambient `FASTEMBED_CACHE_DIR`/`HF_HOME` — precisely the class INV-5 exists to forbid, and on a macOS `.app` the CWD is `/`.

**3. Collapsing to one process deletes a fault boundary the plan never replaces (B-04, CRITICAL).**
INV-1 removes the child process. `[profile.release] panic = "abort"` (`src-tauri/Cargo.toml:126-131`) means that after the restructure a panic in any tool, adapter, subagent or worker turn **aborts the whole application**, losing every concurrent session. Today a Python worker crash is contained by the OS. Nothing in ten specs mentions fault isolation, supervision, or recovery of in-flight sessions. The plan treats the process boundary purely as cost; it is also insulation.

**4. ADR-01-02's stated cost is the wrong cost, and no slice schedules the work (B-05, B-06, HIGH).**
The ADR says extraction is "a real refactor, since `AgentEngine` currently reaches into `AppState`". `AppState` is 62 lines of scalars (`state/app_state.rs:14-61`) — an afternoon. The actual entanglement is a **process-global `static APP_HANDLE: OnceLock<AppHandle>`** (`events.rs:14-19`) feeding **132 `emit_*` call sites across 27 files**, eleven of them inside `agent/builtin_tools/`. And Part 6's nine slices contain **no work at all** for `autodev-core`, `src-cli` or `src-shared`, despite ADR-01-02 and ADR-01-03 both being **BLOCKS CODE** and both answered "full scope". If the extraction lands after P2/P3, the provider layer and the runtime get refactored twice.

**5. The P8 entry gate cannot be met as written (B-08, HIGH).**
"All nine ported capabilities pass with the sidecar not running" is measured against `G1 §C.4`, where capability **P4 is "multi-provider LLM routing — 10 provider families"** and capability **P7 is the fleet-readiness startup FSM**. The mandate ships **four** providers ("Anthropic, OpenAI, Gemini, Grok. Exactly these"), and OQ-3 removes Demo Mode while P8 deletes `get_startup_phase`. Two of the nine are, by decision, not being ported. The gate is therefore either unmeetable or is quietly reinterpreted at the moment it is applied — which is how a gate stops being a gate.

**6. The cost-honesty proof is built on a provider-specific identity applied to all four providers (B-09, HIGH).**
Spec `02 §4.2` states `total_input = cache_read + cache_creation + input`. That is Anthropic's model, where `input_tokens` **excludes** cached tokens. OpenAI's `prompt_tokens` and Gemini's `promptTokenCount` are **inclusive** of their cached counts, and reasoning tokens are reported inside output totals on OpenAI/Gemini rather than beside them. Summing the six `Usage` fields as disjoint double-counts on two to three of the four providers — which fails product-proof #1 ("reported cost matches the provider's own billing") in exactly the subtle way the plan says it wants to avoid.

**7. Keychain-only BYOK has no Linux answer (B-10, HIGH).**
INV-12 says the runtime "reads the keychain or fails loudly". `keyring 2.3.3` (Cargo.lock:3211) resolves on Linux to the D-Bus Secret Service, which requires a running **and unlocked** `gnome-keyring`/KWallet. Spec `09 §2.1` correctly notes the missing `deb` dependency — but a declared dependency does not make a daemon *run*. On a headless or minimal Linux install, AutoDev becomes unusable with no permitted fallback, and the project's own CI already documents the absence (`ci.yml:64-65`: *"require a display/keychain not present in CI"*), which makes `G-KEY-ASYM` and `G-KEY-NOENV` unrunnable in the blocking CI that ADR-04-03(A) mandates.

**8. Two mechanics are five mechanics, and Part 1B was not re-costed after Group E (B-15, MEDIUM).**
M-10 still reads *"Three tiers in-house over SQLite; **lexical retrieval; seam left for a vector index**"* with balance *"MATH (+EMB if ADR-01-07 says so)"*. ADR-01-07 was overturned; ADR-05-01…05-05 replaced M-10 with: a vector substrate, an ONNX embedding runtime with a model lifecycle and first-run UX, hybrid retrieval with fusion and reranking, a scope/provenance schema, a write-permission gateway, and an IR evaluation suite (Recall@k, MRR). The header still says "29 mechanics across five workstreams"; there are **39 across six**. P3's size is calculated from the stale text.

## 3 · The `sqlite-vec` + `rusqlite` + `fastembed` stack

This is the newest and least evidenced part of the plan — ADR-05-01 and ADR-05-02 were both written and answered on the day the ledger closed — so it gets its own section. I was asked to test the linking claim hard. **It holds. The claims around it do not.**

### 3.1 The suspicion that was wrong — there is no duplicate SQLite

The brief suspected `sqlite-vec` and `rusqlite`'s `bundled` feature would fight over the SQLite amalgamation. **They do not.** Verified:

- `libsqlite3-sys 0.28.0` (`Cargo.lock:3332`) compiles the amalgamation with `-DSQLITE_CORE -DSQLITE_ENABLE_FTS5 -DSQLITE_ENABLE_LOAD_EXTENSION=1 -DSQLITE_THREADSAFE=1` (`build.rs:122-138`, vendored under `~/.cargo/registry/src/index.crates.io-*/libsqlite3-sys-0.28.0/`). **FTS5 is present in the bundled build** — the plan's BM25 leg is real, not aspirational.
- `sqlite-vec 0.1.9`'s entire `build.rs` is `cc::Build::new().file("sqlite-vec.c").define("SQLITE_CORE", None).compile("sqlite_vec0")`. It ships `sqlite3.h` / `sqlite3ext.h` **headers only** — no `sqlite3.c`. It has **no runtime dependencies at all**; `rusqlite 0.31.0` appears only as a *dev*-dependency, which is exactly the version this workspace pins. ([docs.rs source](https://docs.rs/crate/sqlite-vec/latest/source/build.rs))
- `sqlite3_auto_extension` is exported by `libsqlite3-sys` in the non-`loadable_extension` configuration as a hand-written `extern "C"` block (`bindgen-bindings/bindgen_3.14.0.rs:4-13`; the blocklist-and-replace logic that emits it is at `build.rs:546-566`). The documented registration path therefore compiles.

**Verdict: ADR-05-01's core technical claim is sound.** One statically-linked SQLite, one extension object linked beside it, FTS5 built in, no server, no port, no second process. INV-1 holds. This part of the plan should proceed.

### 3.2 What is wrong around it

| # | Claim | Reality | Severity |
|---|---|---|---|
| 1 | *"No extension loading"* (ADR-05-01) | The registration mechanism **is** the auto-extension hook — a **process-global** callback that affects only connections opened **after** it runs, registered through an unchecked `transmute` of a function pointer. There are **21 `Connection::open` call sites** in `src-tauri/src`, none of which today coordinate with a startup hook, and `airsctl` is a separate process that must register independently (B-13) | MEDIUM |
| 2 | *"Metadata filtering → plain SQL columns"* | `vec0` KNN filtering is restricted to declared **metadata** and **partition-key** columns; anything else errors or is silently wrong. Scope-as-mandatory-filter (ADR-05-03) cannot be a post-KNN join (B-01) | **CRITICAL** |
| 3 | Implied: recall cost is roughly constant | The released `vec0` performs an **exhaustive scan**; ANN structures (IVF, DiskANN) exist in-tree but are not part of the released extension. At 384 dims x f32 = 1.5 KB per vector, a 100k-memory corpus is ~150 MB read per query, plus the embedding inference. Fine at small scale — but it is a **linear** function of how much the user remembers, and the plan sets no cap and no measurement | MEDIUM (`SUSPECTED` on ANN status; settle by reading the CHANGELOG for the pinned version) |
| 4 | Stability | `sqlite-vec` is **0.1.9** and its README says *"pre-v1, so expect breaking changes"*. It is being placed under the memory subsystem of a product whose thesis is removing fragile dependencies | MEDIUM — pin exactly, vendor if possible |
| 5 | Link order | `sqlite-vec` declares **no dependency** on `libsqlite3-sys`, so Cargo has no edge forcing `libsqlite_vec0.a` to precede `libsqlite3.a` on the link line. MSVC and ld64 are order-insensitive for archives; **GNU ld is not**. This combination is widely used on Linux, so the risk is low but non-zero | LOW-MEDIUM, **SUSPECTED** — settle with one Linux build in the P3 spike; the fix if it bites is a `build.rs` link-arg or `--start-group` |
| 6 | Backup and tooling | Once `memory.db` contains a `CREATE VIRTUAL TABLE … USING vec0(…)`, any process without the module registered fails on statements touching it — including the scheduled `VACUUM` adopted in OQ-5, and any `sqlite3`-CLI-based backup or support workflow | MEDIUM |

### 3.3 `fastembed` — the dependency nobody costed

ADR-05-02 presents local embeddings as: one crate, one 130 MB model, synchronous, offline after first run. The manifest says otherwise (fastembed 6.0.2, [docs.rs](https://docs.rs/crate/fastembed/latest/source/Cargo.toml)):

```
ort        = "=2.0.0-rc.13"   (features: ndarray, std, api-24; default-features = false)
hf-hub     = "0.5.0"          (optional; ureq / native-tls / rustls-tls)
tokenizers = "0.22.2"         (onig)
ndarray    = "0.17.2"
safetensors = "0.8.0"
default    = ["ort-download-binaries-native-tls", "hf-hub-native-tls", "image-models"]
```

Consequences the plan does not mention anywhere:

1. **Build-time network dependency.** `ort-download-binaries` fetches a prebuilt ONNX Runtime from pyke's CDN during `cargo build`. Every CI runner, every clean developer machine and every release build acquires a third-party binary at build time. That sits badly beside INV-3's supply-chain posture and makes offline or air-gapped builds impossible without vendoring.
2. **An exact-pinned release candidate** (`=2.0.0-rc.13`) becomes load-bearing for memory. RC-to-RC breaks in `ort` are routine, and a `fastembed` upgrade drags the pin.
3. **Native library placement, per platform.** Where `ort` resolves to compile-time dynamic linking, the shared library must sit beside the executable (Windows) or on the loader path / under an rpath (Linux, macOS) ([ort linking](https://ort.pyke.io/setup/linking)). For a Tauri app that means a **new bundle resource, signed on macOS and included in notarisation** — work that belongs to M-27 / ADR-04-02 and is not in it. Whether static linking applies on all four target triples must be *measured*, not assumed.
4. **`image-models` is a default feature** and is not needed; it pulls `image 0.25`. Disable it.
5. **`native-tls`** on Linux means OpenSSL at build and runtime, adding a `deb` dependency beside the `libsecret` one spec `09 §2.1` already found. `rustls-tls` variants exist and should be preferred for a shipped desktop app.
6. **Workspace feature unification** means `airsctl` links ONNX Runtime too (B-03), because `autodev-core` (ADR-01-02) will be a shared dependency. Feature-gate the embedder, or the CLI's build time and binary size inherit the whole ML stack.
7. **Cache path** — the INV-5 violation in B-02.
8. **Panic behaviour.** ONNX Runtime is C++. `ort` surfaces most failures as `Result`, but an abort inside the native runtime under `panic = "abort"` takes the whole app with it (B-04).

### 3.4 What I would do instead

Not "drop the stack" — the substrate decision is right for a desktop app and the anchor's trifecta genuinely fits. Do this:

- **Run a spike before P3 is scheduled**, producing `MEASURED` numbers: builds green on Windows x64, macOS arm64, macOS x64 and Linux x64; static-vs-dynamic link mode per platform; binary-size delta; cold and warm embedding latency; `vec0` KNN latency at 1k / 10k / 100k memories; and one end-to-end scoped recall proving pre-filtering works.
- **Rewrite ADR-05-01's mechanism paragraph** to say what actually happens: auto-extension registration, metadata and partition columns for filtering, exhaustive KNN.
- **Own the model download** (B-16) and always pass an explicit `cache_dir` (B-02).
- **Keep the retrieval-backend trait honest:** it must expose *filtered* KNN — `search(query_vec, k, scope_filter)` — not `search(query_vec, k)` with filtering left to the caller, or the seam bakes the post-filter bug into the architecture.

## 6 · Proposed new ADRs — Group G

Six decisions this review opens. Each needs an owner answer before the slice it blocks.

### ADR-G-01 — The Linux credential store under keychain-only BYOK — BLOCKS CODE (P0 / P7)
**The call:** INV-12 says "keychain or fail loudly". On Linux the keychain is a D-Bus Secret Service that may be absent, locked, or unavailable in CI and in containers. What does AutoDev do?
**Why it matters:** It decides whether the headline acceptance test passes on a legitimate Linux install, and whether `G-KEY-ASYM` / `G-KEY-NOENV` can run in the blocking CI that ADR-04-03 mandates. `keyring 2.3.3` compiles both the Secret Service and kernel-keyutils backends; the latter does not survive a reboot, so it is not a silent substitute.
**Options:** **(A)** Keychain only; on Linux without a secret service AutoDev refuses to store a key and says why. **(B)** A `SecretStore` trait — OS keychain by default, plus an explicit, user-chosen, file-based encrypted store when no service is available, with the active backend shown in the UI. **(C)** Keychain plus keyutils as an automatic fallback.
**My recommendation:** **(B)**. (A) makes a supported platform unusable in ordinary configurations; (C) is a silent fallback with surprising loss-on-reboot semantics — exactly the "presence of a capability is not intent to use it" failure INV-12 exists to prevent. (B) keeps the choice explicit and testable and gives CI a real backend, so the key gates can actually block.

### ADR-G-02 — How provider conformance blocks CI — BLOCKS CODE (P2)
**The call:** `G-CONFORM` and `G-CACHE-HIT` are blocking gates that make live calls to four vendors. Where do the credentials come from, what happens on a vendor 529, and what runs on a fork PR?
**Why it matters:** Without an answer the gate is quietly made non-blocking — reproducing today's `continue-on-error` state under a new name, and violating INV-4 at the one place the restructure most needs proof.
**Options:** **(A)** Live suite blocking on every PR, secrets in CI. **(B)** Two tiers — recorded-fixture conformance blocking on every PR (wire shapes, tool-arg round trip, usage parsing, truncation mapping, error classification), live conformance nightly and alerting. **(C)** Live suite blocking on `main` only.
**My recommendation:** **(B)**. It is the only option that is both honest about "blocking" and immune to vendor weather, and the fixtures double as the regression corpus when an adapter is rewritten. Add the rule: *a test that skips because a precondition is missing has failed.*

### ADR-G-03 — Where scope lives in the `vec0` schema — BLOCKS CODE (P3)
**The call:** ADR-05-03 makes scope a mandatory retrieval filter. In `vec0`, only metadata and partition-key columns can filter a KNN query. Which columns are which?
**Why it matters:** Get it wrong and scoped recall post-filters the top-k, returning fewer results than requested and zero for selective scopes — a silent starvation defect in the subsystem whose entire purpose is recall.
**Options:** **(A)** `tier` and `scope_kind` as partition keys; `scope_id`, `agent_id`, `source` as metadata columns; text bodies and provenance detail in an ordinary table joined by rowid. **(B)** One `vec0` table per tier, scope as metadata. **(C)** Scope in ordinary SQL with an over-fetch factor (`k × N`) and post-filtering.
**My recommendation:** **(A)**, and require the retrieval-backend trait to take the filter as an argument so the seam cannot hide a post-filter. (C) is defensible only as a fallback, with a measured over-fetch factor and a gate asserting result counts.

### ADR-G-04 — Fault isolation after the process collapses to one — BLOCKS CODE (P3 / P4)
**The call:** With INV-1 and `panic = "abort"`, any panic in agent code destroys the whole app and every session. What replaces the process boundary the sidecar provided?
**Why it matters:** It is the unpriced cost of the plan's central move, and it lands exactly when tens of thousands of lines of new agent code arrive.
**Options:** **(A)** `panic = "unwind"` in release plus a per-turn catch boundary that fails the turn, not the app. **(B)** Keep `abort`, make turn state crash-durable (persist each `Item` as it is produced, per spec `01 §3.2`) and auto-resume on restart. **(C)** Both.
**My recommendation:** **(C)**, sequenced (A) then (B). (A) is a two-line profile change plus a boundary and buys immediate containment; (B) is what makes a crash survivable rather than merely non-fatal, and spec `01 §3.2` already requires the per-item persistence it depends on. Gate: inject a panic in a tool mid-turn; the app survives and the session reloads intact.

### ADR-G-05 — Provider-hosted tools versus the effect boundary — BLOCKS CODE (P2 / P3)
**The call:** ADR-02-08(B) adopts hosted web search **and file search**; OQ-4 and ADR-01-05 row 8 name different vendors for search. Hosted tools execute outside `ToolRegistry`, outside the permission gate, and — for file search — upload the user's repository to the vendor and create server-side objects.
**Why it matters:** Spec `06` classifies the same behaviour as a defect when a local tool does it (`analyze_diff` uploading a full repo diff unprompted) and introduces `ToolEffect::Network` to gate it. Adopting hosted file search without that gate contradicts the plan's own security model and creates vendor-side data with no lifecycle owner.
**Options:** **(A)** Web search only, one named vendor, gated as `ToolEffect::Network` and visible in the turn transcript. **(B)** Web plus file search, with an upload consent prompt, a retention policy and a delete path. **(C)** No hosted tools; every effect is ours.
**My recommendation:** **(A)** for the restructure, with file search deferred to a follow-up carrying its own data-residency answer. And reconcile the vendor: one decision, in one place.

### ADR-G-06 — The unsupported-parameter policy across providers — BLOCKS CODE (P2)
**The call:** ADR-01-04's answer asks for "all inputs are there but dropped per provider". Dropping is what OpenAI and Google do to `max_tokens` today, and it is the defect M-03 exists to remove.
**Why it matters:** It decides whether `G-MAXTOK` and the conformance family can pass, and whether a user who sets a reasoning effort on a model that has none is told or ignored.
**Options:** **(A)** Unsupported parameter yields a typed `ProviderError::Unsupported` and the request is refused. **(B)** Downgrade silently. **(C)** Downgrade, but record it on the turn and surface it once in the UI.
**My recommendation:** **(C)** for cosmetic parameters and **(A)** for anything that changes correctness or cost — `max_tokens`, tool schemas, structured output, cache policy. Also restate the "singleton" wording as *one shared transport, one trait, per-provider adapters*: a single object serving four vendors cannot hold four base URLs, four auth schemes and xAI's per-conversation cache affinity.

## 7 · What I would keep exactly as it is

An adversarial review that only attacks is not calibrated. These parts of the plan are stronger than typical and should not be diluted in response to anything above.

- **INV-8 (a writer must have a proven reader)** and the Reader-exists test family. This is the single best mechanism in the document, and it is what most of the ~415-defect register is made of.
- **Guard-the-guard, constructed the way production constructs it.** Precisely the discipline that would have caught `ToolContext.depth = 0` at three sites.
- **ADR-02-02(A)** — deterministic build verification, with the model demoted to a debug aid after three failures. The exit code of a build is a fact, not a judgement.
- **ADR-05-01's substrate choice.** SQLite + `sqlite-vec` + FTS5 is right for this product, and the linking claim survives scrutiny (§3.1). Fix the filtering design; keep the decision.
- **P8 as its own gated phase**, and the coupled-deletion note on `bridge.rs`'s SSE frame parsers. Both are correct and specific.
- **The append-only ledger with struck-through retractions** (ADR-05-02). It is the reason this review could tell which numbers had been superseded and which had merely been repeated.
